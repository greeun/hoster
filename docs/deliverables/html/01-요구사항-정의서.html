요구사항 정의서

앵커 비유: 입주 전 관리사무소와 맺는 "해주기로 한 일 목록" — 항목마다 도장이 찍히거나 빈칸으로 남습니다. 이 문서는 hoster가 하기로 한 일 45건(기능 요구사항 28 + 비기능 요구사항 17)을 검인 보드 위에 늘어놓고, 실제로 코드에 없는 3건은 정직하게 빈칸으로 둡니다.

0처음 보는 말 — 먼저 풀어둡니다

본문에서 이 말들을 다시 만나면 전부 여기 적은 뜻입니다. 여기서 한 번 풀어두고, 본문에서는 다시 설명하지 않습니다.

컨테이너 — 내용물이 무엇이든 규격이 같아 어디서든 그대로 옮길 수 있는 표준 이사짐 상자
이미지 — 컨테이너를 찍어내는 원판. 같은 이미지면 언제 열어도 내용물이 같음
레지스트리(ghcr.io) — 포장된 상자를 맡아 두는 물류 창고
터널 — 정문을 열지 않고 안에서 밖으로 미리 뚫어 둔 전용 통로
리버스 프록시(Traefik) — 동·호수 팻말을 보고 배달할 세대를 정해주는 경비실 안내데스크
DNS/CNAME — 간판 주소(도메인)를 실제 배송지에 연결해 두는 주소록 등록
HMAC(서명) — 우리 둘만 아는 인주로 찍은 도장. 도장이 같아야 접수됨
타임스탬프 허용 오차 — 접수증 시각이 너무 오래됐으면(5분 초과) 반려하는 규칙
헬스체크 — 새 설비가 실제로 불이 들어오는지 확인하는 점검
롤백 — 새 물건에 하자가 있으면 원래 물건을 다시 꺼내 놓는 것
배포 큐 — 접수창구에 밀려드는 요청을 순서대로 처리하는 대기줄
부트스트랩 — 관리사무소를 처음 여는 개소(開所) 준비 절차
드라이런(dry-run) — 실제로 도장을 찍지 않고 서류만 미리 검토해 보는 예행연습
멱등 — 같은 신청서를 두 번 접수해도 결과가 한 번 접수한 것과 똑같은 것
WAL(저널 모드) — 장부에 바로 옮겨 적기 전에 먼저 써 두는 임시 메모장
dockerode — 관리사무소가 상자(컨테이너)를 다루는 손발이 되어주는 프로그램 부품

1배경 → 목표 — 왜 이걸 만들었나

NAS라는 특수한 환경이 강제한 제약 4가지가, hoster가 하기로 한 일 4가지로 이어졌습니다.

2요구사항 전체 지형 — 검인 보드

"해주기로 한 일 목록" 45건을 접수 도장칸으로 늘어놓았습니다. 도장을 누르면 문구와 구현 위치가 펼쳐집니다.

규모 비교 — FR 28 · NFR 17

3배포 파이프라인 — push부터 롤백까지

코드가 push되면 어떤 순서로 상자가 포장되고 배달되는지, 요구사항 번호를 따라가 봅니다.

4보안 요구사항 — 어디를 어떻게 막는가

밖에서 들어오는 것 4가지가, 각각 다른 관문을 통과해야 관리사무소 안으로 들어옵니다. 상세한 관문은 07번 문서가 다룹니다 — 여기서는 요구사항 수준으로 얕게.

5제약사항 13항목

NAS 환경이 이미 정해 놓은 규칙들 — 못 하게 된 것과, 대신 택한 방법입니다.

6구현 위치 — 어느 파일에 몰려 있나

45건의 요구사항이 실제로 어느 파일에 근거하는지, 얼마나 몰려 있는지를 봅니다. 자세한 모듈 구조는 03번 문서가 다룹니다.

7이름 규칙 — 프로젝트명과 공개 도메인

서식에 아무 이름이나 쓸 수 없습니다. 정해진 칸에 정해진 모양으로만 적어야 접수됩니다.

8이 문서가 말하지 않는 것 — 범위 제외 · 미구현 3건

이 절은 이 문서의 정직성입니다. 축소하거나 "곧 될 것"처럼 쓰지 않습니다 — 코드에 없다고 원문이 단정합니다.

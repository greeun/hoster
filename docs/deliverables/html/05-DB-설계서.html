05. DB 설계서

세대 대장과 배송 일지 — 관리사무소 장부실에는 장부가 두 권 있다. 왼쪽은 세대 대장(projects), 오른쪽은 배송 일지(deployments)다. 두 장부는 같은 이름을 적지만, 서로 실로 묶여 있지 않다 — 세대를 지워도 배송 일지는 그대로 남는다.

대상: packages/deployer (StateStore, src/store.ts) 버전 1.0 작성일 2026-08-13 원문: docs/deliverables/05-DB-설계서.md
지금 보고 있는 곳: 단지 배치도(02번 문서 자산의 축약판) 위에서, 이 문서는 관리사무소 안쪽의 장부실 — deployer의 SQLite 상태 저장소를 다룬다. 창구에서 접수한 서식이 여기 장부에 어떻게 기록되는지가 이 문서의 범위다.

시그니처두 권의 장부 펼침면

1층. 왼쪽 페이지는 세대 대장, 오른쪽 페이지는 배송 일지다. 가운데 노란 줄로 표시된 "이름" 칸이 서로 같은 값을 적긴 하지만, 실로 꿰매어 묶여 있지는 않다 — 관리사무소가 세대 카드를 파기해도 배송 일지의 옛 기록은 그대로 남는다. 아래 버튼으로 세대를 지워 보면, 실제로 무슨 일이 일어나는지 확인할 수 있다.

1FK 없음이 낳는 결과 — 호출 순서 비대칭 도해

1층. "배송 접수(deploy)"와 "반송 접수(rollback)"는 같은 일을 반대 순서로 한다. 배송은 일지부터 적고 나중에 세대를 확인하고, 반송은 세대부터 확인하고 나중에 일지를 적는다. 그래서 등록 안 된 세대로 배송을 시도하면 일지엔 기록이 남지만, 반송을 시도하면 아예 일지에 흔적조차 남지 않는다.

2층 · 기술 상세FK 부재가 낳는 3가지 실제 결과
  1. 프로젝트를 지워도 배포 이력은 고아 행그 줄이 가리키던 세대가 이미 지워졌는데도 장부에 그대로 남아있는 줄으로 남는다(removeProject는 DELETE FROM projects만 실행, deployments는 손대지 않음).
  2. deploy 경로는 미등록 프로젝트로도 deployments 행이 먼저 생긴 뒤 실패 처리된다 — execute()가 recordDeployment(orchestrator.ts:113)를 getProject 확인(:114-115)보다 먼저 호출.
  3. rollback 경로는 반대라 행 자체가 안 생긴다 — doRollback()은 getProject 확인(:139-141)이 recordDeployment(:143)보다 먼저.

deployments.project는 TEXT이며 FK다른 장부의 어느 줄을 가리키는지 표시해 두 장부를 묶어주는 실(FOREIGN KEY) 절이 CREATE TABLE 원문에 없다 — 참조 무결성이 DB 레벨에서 보장되지 않는다.

2deployments.status 상태 전이

1층. 일지의 한 줄은 항상 "대기(pending)"로 시작해서, 딱 한 번 다른 도장으로 바뀌고 멈춘다 — 성공, 실패, 또는 롤백 완료. 자기 자신으로 되돌아오는 화살표는 없다. 아래 시나리오 버튼을 누르면 점이 실제로 그 경로를 따라 움직인다.

대기 · pending 성공 · success 실패 · failed 롤백 완료 · rolled_back

이 네 도장의 색은 시리즈 전역에서 의미가 고정되어 있다 — 다른 9개 문서에서도 같은 색은 항상 같은 뜻이다(§3.0 공통 상태 색).

시나리오를 선택하면 점이 pending에서 실제 도착 상태까지 이동한다.

4장부는 실제로 어디에 있는가 — 경로 대응 도해

1층. 컨테이너 안에서 보는 서랍 이름과, NAS 캐비닛의 진짜 서랍 이름은 다르다. 볼륨 마운트컨테이너 안의 특정 서랍을 NAS의 실제 캐비닛 서랍과 같은 것으로 연결해 두는 것가 둘을 같은 서랍으로 만들어 준다.

2층 · 기술 상세compose 볼륨 마운트 원문

stack/docker-compose.yml의 deployer 서비스 volumes: /volume1/docker/hoster/state:/state. 컨테이너 내부에서는 process.env.STATE_DIR ?? '/state'로 접근하고, envDir = join(stateDir, 'env'). env 파일 하나의 형식은 줄 단위 KEY=VALUE, 파일 끝 개행.

5장부 서식 원문 — 주석 달린 코드 패널

1층. 장부 두 권을 처음 펼칠 때 쓰는 서식 원본이다. 매번 문을 열 때마다 "이 서식이 있는지"만 확인하고 없으면 새로 찍어낸다 — 서식 칸 자체를 나중에 고치는 도구는 없다.

CREATE TABLE IF NOT EXISTS projects (
  name TEXT PRIMARY KEY,              ← 이 줄이 이 장부의 대표 번호
  image_repo TEXT NOT NULL, domain TEXT NOT NULL,
  branch TEXT NOT NULL, health_path TEXT NOT NULL, container_port INTEGER NOT NULL,
  current_image TEXT, previous_image TEXT
);
CREATE TABLE IF NOT EXISTS deployments (
  id INTEGER PRIMARY KEY AUTOINCREMENT, ← 번호표가 자동으로 하나씩 올라감
  project TEXT NOT NULL,                ← projects.name을 가리키지만 FOREIGN KEY 절이 없다
  image TEXT NOT NULL, sha TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending', error TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))  ← UTC 기준
);
2층 · 기술 상세스키마 관리 방식

스키마 관리는 CREATE TABLE IF NOT EXISTS 뿐이며, 생성자 실행 시마다 멱등같은 접수증을 몇 번 다시 내밀어도 결과가 달라지지 않는 성질하게 실행된다. 별도의 마이그레이션장부의 칸 구성 자체를 바꾸는 개조 공사 — 이 시스템에는 그 개조 도구가 없다 도구는 없다. id 컬럼의 AUTOINCREMENT는 새 줄마다 번호표가 자동으로 올라가는 방식이고, status는 updateDeploymentStatus가 허용하는 값만 들어간다: 'pending' | 'success' | 'failed' | 'rolled_back'. rollback 요청의 sha 컬럼에는 리터럴 문자열 'rollback'이 그대로 들어간다. created_at의 datetime('now')는 UTC 기준장부에 시각을 적을 때 한국 시간이 아니라 세계 표준시로 적는다는 규칙이다 — 한국 시간(KST)보다 9시간 이르게 찍힌다.

근거: packages/deployer/src/store.ts:21-33 · 05-DB-설계서.md § 3.1

6일지를 펼치면 최근 20줄만 보인다 — 장부 창 도해

1층. GET /status/:project로 일지를 펼치면 전체가 다 나오는 게 아니라, 가장 최근 20줄만 유리창 너머로 보인다. 그보다 오래된 줄은 여전히 장부 속에 있지만, 이 창구로는 보이지 않는다.

2층 · 기술 상세어느 API가 이 창을 쓰는가

listDeployments 기본 limit=20은 GET /status/:project에서만 쓰인다. GET /status(전체 목록)는 projects 테이블만 SELECT * FROM projects ORDER BY name으로 읽으며 배포 이력 자체를 포함하지 않는다 — 이 창은 "프로젝트 하나의 이력"에만 해당한다.

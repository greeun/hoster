09. 설치·운영 매뉴얼

관리사무소가 새 단지에 설비(hoster 스택)를 처음 들이는 개통 절차와, 입주 이후 평소 점검·장애 대응·백업까지를 다룬다. 대상 독자는 NAS/Cloudflare/GitHub 인프라를 직접 관리하는 운영자다.

01

준비물 배치도 — 어디에 무엇이 갖춰져 있어야 하나

개통 전 세 곳(로컬 Mac · NAS · 외부 서비스)에 총 9종의 준비물이 갖춰져 있어야 한다. 하나라도 빠지면 12단계 중 특정 단계에서 걸린다. 이 개통 절차(hoster init)는 평소에 반복하는 일이 아니라, 맨 처음 딱 한 번만 치르는 부트스트랩아무것도 없는 상태에서 최소한의 것부터 차례로 갖춰 나가 전체를 처음 일으켜 세우는 절차 — 새 건물의 최초 준공·개통과 같다이다.

🖋 1층 — 이사 오기 전 관리사무소가 확인하는 준비물 목록과 같다. 열쇠(Mac), 출입증(NAS 접속), 그리고 외부 기관 서류(Cloudflare·GitHub) 세 종류가 모두 있어야 개통을 시작할 수 있다.

04

재실행의 위험 — HMAC_SECRET이 다시 찍힌다

hoster init을 다시 돌리면 새 HMAC우리 둘만 아는 인주로 찍는 도장 — 본문과 시각을 섞어 계산하는 서명값 비밀키가 생긴다. 이미 등록된 레포의 GitHub 시크릿은 옛 값 그대로 남는다.

도장 불일치 — NAS의 새 도장 vs 레포에 남은 옛 도장

NEWHMAC_SECRET

재실행 직후 NAS .env와 ~/.hoster/config.json에 반영된 새 비밀키

≠
OLDHOSTER_DEPLOY_SECRET

등록된 레포의 GitHub 시크릿은 그대로 — 서명 검증 실패 (401 invalid signature)

재동기화 조치 재실행 후 등록된 레포마다 hoster add(또는 수동 gh secret set HOSTER_DEPLOY_SECRET)로 시크릿을 다시 맞춘다.

경고 — 업그레이드 목적으로 hoster init 전체를 재실행하지 말 것. 업그레이드 절차는 §7에 따로 있다.

05

NAS 스택 운영 — 평소 확인

compose 파일은 /volume1/docker/hoster에 있다. 세 컨테이너 모두 restart: unless-stopped라 NAS 재부팅 시 자동 복구되고, 상태(SQLite)는 볼륨 마운트컨테이너 내부 폴더를 NAS의 실제 폴더에 그대로 연결해, 컨테이너를 지워도 데이터가 남게 하는 것로 영속된다.

컨테이너 3종 상태 보드

hoster-cloudflared

터널 연결 담당 · Up 상태여야 정상

hoster-traefik

리버스 프록시(경비실 안내데스크) · Up 상태여야 정상

hoster-deployer

배포 처리(관리사무소) · Up 상태여야 정상

목적명령
상태 확인ssh -p 2222 admin@192.168.1.100 'sudo -n /usr/local/bin/docker ps'
로그 확인(compose)cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose logs -f [cloudflared|traefik|deployer]
앱 로그(로컬에서)hoster logs <project> [--tail <n>] — 기본 tail 200
전체 재기동cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose --env-file .env up -d
개별 재시작sudo -n /usr/local/bin/docker restart hoster-<cloudflared|traefik|deployer>

🖋 1층 — 세 설비실 계기판이 모두 "가동 중"이어야 단지가 정상이다. 정전(재부팅)이 나도 설비는 스스로 다시 켜지지만(unless-stopped), 장부(SQLite)는 별도 캐비닛에 있어 설비를 갈아도 지워지지 않는다.

업그레이드 — deployer 이미지 재빌드·재전송

3절 8단계와 동일한 명령을 그대로 재사용한다.

업그레이드 명령

Mac에서 빌드·전송 → NAS에서 재기동

docker buildx build --platform linux/amd64 \
  -f packages/deployer/Dockerfile -t hoster-deployer:latest --load .
# linux/amd64로 고정 빌드 — NAS 자체에서는 빌드하지 않음

docker save hoster-deployer:latest | gzip | \
  ssh -p 2222 admin@192.168.1.100 'gunzip | sudo -n /usr/local/bin/docker load'
# save|gzip|ssh|load — 이미지를 압축해 통째로 NAS에 밀어넣는다

cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose --env-file .env up -d
# 태그가 hoster-deployer:latest로 고정이므로 load 직후 up -d가 새 이미지로 재기동
  • state/(hoster.db, env/)는 볼륨 마운트이므로 컨테이너 재기동과 무관하게 보존된다.
  • 업그레이드 목적으로 hoster init 전체를 재실행하지 말 것 — HMAC_SECRET이 재생성되어 기존 레포 시크릿과 불일치(§4)가 생긴다. 업그레이드는 이 세 명령의 수동 반복만으로 충분하다.

시각물 7 · 주석 코드 패널 — 3절 8단계와 동일 명령의 재사용임을 강조.

🖋 1층 — 설비를 새 것으로 바꿀 때, 장부(state/)가 든 캐비닛은 그대로 두고 설비 본체만 통째로 새로 들여와 갈아 끼우는 것과 같다.

2층 기술 상세 펼치기

이미지 태그가 hoster-deployer:latest로 고정이므로 docker load 직후 up -d가 새 이미지로 재기동한다. 3절 8단계와 정확히 동일한 명령을 재사용한다.

08 · 이 문서가 말하지 않는 것

다루는 것과 다루지 않는 것

확인 못 한 사실 — 09번 §3은 hoster init 프롬프트 순서를 "기본 도메인 → Cloudflare API 토큰 → Account ID → Zone ID → GHCR PAT" 5개로 적었다. 03번 문서(상세 설계서) §4.10 runInit 실행 흐름은 4개만 적어 기본 도메인 프롬프트가 빠져 있다. 소스 코드는 이번 범위에서 확인하지 않았다 — 이 문서는 09 원문의 순서를 그대로 따르고, 어느 쪽이 맞는지 단정하지 않는다.

이 문서의 범위

이 문서가 다루는 것

  • 설치 12단계와 각 단계의 실패/복구
  • NAS 운영 명령(상태·로그·재기동)
  • 장애 대응 5증상
  • 백업 대상 4종과 복구 순서
  • 업그레이드(이미지 재빌드·재전송) 절차

이 문서가 다루지 않는 것

  • 자동 백업 스케줄 — hoster는 제공하지 않음. DSM 표준 도구(Hyper Backup 등)에 위임
  • 모니터링·알림 체계 — doctor/logs를 사람이 수동으로 실행해야 함
  • docs/e2e-checklist.md의 내용 — 경로·역할만 언급, 안의 내용은 지어내지 않음
  • 프로젝트 등록·배포 사용법 — 10. 사용자 매뉴얼 참고

🖋 1층 — 이 서식철은 "단지를 처음 짓고 유지·보수하는 법"만 다룬다. "입주민이 짐을 어떻게 옮기는지"는 다음 서식철(10번) 몫이다.

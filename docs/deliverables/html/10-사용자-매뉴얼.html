02 · 시그니처

push → 공개 URL 여정 지도

hoster는 무중단 배포가 아니다. 교체 중 해당 프로젝트가 완전히 무응답인 구간이 실제로 존재한다 — 미검증 새 버전으로 트래픽이 새는 것을 막기 위한 의도된 트레이드오프다. 새 상자가 제대로 왔는지는 헬스체크문 앞에서 잠깐 "계세요?" 하고 두드려 확인하는 것 — 응답이 없으면 아직 못 받은 것으로 친다로 판정하고, 실패하면 옛 상자로 되돌리는 것을 롤백받은 물건이 잘못됐을 때, 바로 전에 있던 물건으로 되돌리는 것이라 한다. 아래 자를 눈금 삼아, 정상 배포와 실패 롤백의 무응답 폭을 실제 비율로 겹쳐 본다.

②③(가변 구간)은 프로젝트마다 빌드 크기·네트워크 상황이 달라 원문에 시간 근거가 없다 — 폭을 실제 비율로 그리지 않고 같은 너비로만 표시했다. 아래 눈금자는 ④의 무응답 구간만 실제 확정된 초 단위로 그린 것이다.

정상 배포
수 초
실패 → 롤백

정상 배포 막대의 "수 초"는 원문에 정확한 초 수가 없어 눈금 대비 작다는 것만 보여주는 예시 폭이다. 실패 롤백 막대(최대 60초)만 원문에 확정된 숫자(헬스체크 타임아웃)를 그대로 눈금에 맞춰 그렸다.

🖋 1층 — 기존 세대(old 컨테이너)를 옆으로 빼서 정지시킨 뒤에야 새 세대(new 컨테이너)를 들이기 때문에, 그 사이 초인종을 눌러도 아무도 안 나오는 시간이 생긴다. 보통은 금방 끝나지만(수 초), 새로 들인 세대가 문제가 있으면 원래대로 되돌리는 데 최대 1분 가까이 걸릴 수 있다.

2층 기술 상세 펼치기

원인: 기존 hoster-<project> 컨테이너를 hoster-<project>-old로 rename한 직후 즉시 정지 — Traefik이 동일 라우터에 old+new 두 백엔드를 동시에 등록하는 것을 방지하기 위함.

헬스체크: http://hoster-<project>:<port><healthPath>, 기본 60초 타임아웃·1초 간격 재시도.

배포 요청 전송 시 서명: POST $HOSTER_DEPLOY_URL/deploy, 본문 {"project","image","sha"}, 헤더 x-hoster-timestamp/x-hoster-signature (HMAC-SHA256, ${ts}.${body}를 HOSTER_DEPLOY_SECRET으로 서명).

환경변수코드에는 적어두지 않고 실행할 때 옆에서 몰래 알려주는 값 — 접속키·비밀번호 같은 것을 코드 밖에 따로 보관할 때 쓴다 관리 — set에만 있는 것

값은 NAS에만 저장된다 — 레포·워크플로 어디에도 노출되지 않는다.

env set vs env rm

비대칭 — --redeploy는 set에만 있다

hoster env set KEY=VALUE [KEY2=VALUE2 ...] [--project <name>] [--redeploy]
#                                                          ^^^^^^^^^^^ set에만 존재
#   --redeploy 지정 시: 변경 직후 "현재 이미지"로 재배포 트리거

hoster env rm KEY [KEY2 ...] [--project <name>]
#   rm에는 --redeploy가 없음 — 제거를 즉시 반영하려면
#   별도로 재배포하거나 다음 정상 배포(push)를 기다려야 함
  • 저장 위치: NAS /volume1/docker/hoster/state/env/<project>.env (0600)
  • 값 제약: 키는 [A-Za-z_][A-Za-z0-9_]* 형식만, 값에 개행(\r/\n) 불가 — 위반 시 invalid env key: <key> 또는 invalid env value for <key>
  • 프로젝트 미지정 시 현재 디렉터리의 git origin에서 추론(parseGitHubRepo + projectNameOf, hoster add와 동일 규칙)

🖋 1층 — 서식을 새로 써넣을 때는(set) "즉시 반영해 주세요"를 함께 요청할 수 있지만, 서식을 지울 때는(rm) 그 요청란 자체가 없다 — 지운 뒤 반영은 다음 정상 배송(push)을 기다리거나 따로 요청해야 한다.

05

연속 push — 내 요청은 어떻게 되나

같은 프로젝트에 배포가 진행 중일 때 새 push가 연달아 오면, 대기 중이던 이전 요청은 skipped로 사라지고 최신 것만 실행된다. rollback 요청은 skip 대상이 아니다 — 도착 순서대로 대기한다.

대기줄 — 사용자 관점

Push A진행 중
→
Push Bskipped
→
Push C (최신)대기 → 실행

B가 도착했을 때는 대기 1건이었지만, 곧이어 C가 도착하며 B를 밀어내고 "최신 대기"가 됐다. A가 끝나면 C만 실행되고, B는 이력에 skipped로 남는다.

rollback 요청skip 대상 아님
→
도착 순서대로 FIFO대기 중인 deploy와 별개로 처리

🖋 1층 — 관리사무소 접수창구에 같은 세대 앞으로 서류가 연달아 들어오면, 처리 중인 것 다음으로는 가장 최근 서류만 접수하고 중간 것들은 반송(skipped) 처리한다. 다만 "물건 반송(rollback)" 요청만은 절대 건너뛰지 않고 줄 순서를 지킨다.

2층 기술 상세 펼치기

06

롤백의 한계와 제거의 잔여물 — 하는 일 / 안 하는 일

대비 도해

하는 일

  • hoster rollback — 직전 이미지 1단계로 되돌림 (현재+직전 2개만 보관)
  • hoster remove — deployer 등록·실행 중인 컨테이너 정지/제거
  • hoster remove — Cloudflare DNS 레코드 삭제 (관례 추정이 아닌 hoster status로 조회한 실제 도메인 값 사용)

안 하는 일

  • 2단계 이전으로 롤백 — 직전 이미지가 없으면 롤백 실패: no previous image
  • .github/workflows/hoster-deploy.yml 자동 삭제 — 레포에서 직접 삭제해야 이후 push가 /deploy를 더 이상 호출하지 않음
  • GitHub 레포 시크릿(HOSTER_DEPLOY_URL, HOSTER_DEPLOY_SECRET) 자동 삭제 — 필요 시 gh secret delete로 수동 정리

🖋 1층 — 이사 나갈 때 관리사무소는 열쇠와 우편함 이름표는 회수하지만(하는 일), 우편함에 걸어둔 개인 자물쇠와 우체국에 등록해 둔 전달 신청서까지 대신 해지해 주지는 않는다(안 하는 일) — 그건 이사 나가는 사람이 직접 정리해야 한다.

2층 기술 상세 펼치기

부분 실패 시 안내: deployer 등록/컨테이너 제거가 먼저 성공한 뒤 DNS 삭제가 실패하면 "deployer 등록/컨테이너는 제거되었지만 DNS 레코드(<domain>) 삭제에 실패했습니다: ... Cloudflare 대시보드에서 직접 삭제하세요."

브랜치명은 CLI와 deployer 양쪽에서 동일 규칙으로 검증되며, .github/workflows/hoster-deploy.yml 템플릿에 삽입되므로 특히 보수적이다. GitHub owner/repo는 ^[A-Za-z0-9._-]+$만 허용 — 위반 시 "GitHub 원격 URL의 owner/repo에 허용되지 않는 문자가 포함되어 있습니다: <url>".

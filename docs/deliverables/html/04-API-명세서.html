04. API 명세서

deployer가 여는 관리사무소 민원 창구다. 창구마다 정해진 서식라벨 + 밑줄 칸으로 된 기입란 — 요청 본문·파라미터를 담는 그릇이 있고, 서식마다 필수 기입란과 반려 사유가 미리 정해져 있다. 서식이 창구 규정과 하나라도 어긋나면 접수 자체가 반려된다.

대상: packages/deployer (Hono 기반 HTTP API) 버전 1.0 작성일 2026-08-13 원문: docs/deliverables/04-API-명세서.md
지금 보고 있는 곳: 단지 배치도(02번 문서 자산의 축약판) 위에서, 이 문서는 관리사무소 접수 창구 — 즉 deployer가 밖으로 노출하는 HTTP 엔드포인트 9종을 다룬다. 상세한 통행 경로·경비실 구조는 02번 아키텍처 설계서를 확인.

시그니처민원 서식 왕복도

1층. 창구에 서식을 내밀면, 접수 담당자가 순서대로 도장을 검사한다 — 서명 도장이 맞는지, 봉투 속 서류가 제대로 접혀 있는지, 이름칸이 규정에 맞는지(정규식 검증글자가 정해진 칸 모양에 맞는지 자로 재는 규칙), 나머지 칸이 채워졌는지. 하나라도 어긋나면 그 자리에서 반려 도장이 찍히고 뒤 칸은 보지도 않는다. 아래에서 창구를 고르고 칸을 직접 틀려 보면, 실제로 어느 단계에서 반려되는지 확인할 수 있다.

각 관문의 버튼을 눌러 정상/결함 값을 바꾸면 판정이 실시간으로 다시 계산된다 — 색만 바뀌는 연출이 아니라, 실제 검증 순서(서명 → JSON → 이름 정규식 → 개별 필드 → 처리)를 그대로 실행한 결과다.

2층 · 기술 상세왕복도가 구현하는 실제 검증 순서

모든 인증 라우트의 공통 순서: ① HMAC 서명 검증(verifySignature, 실패 시 401) → ② body가 있는 라우트는 JSON 파싱(실패 시 400 invalid json) → ③ PROJECT_NAME_RE 매칭(실패 시 400 invalid project name) → ④ 라우트별 개별 필드 검증 → ⑤ 실제 처리. 이 순서는 packages/deployer/src/app.ts의 라우트 핸들러 코드 순서를 그대로 옮긴 것이며, 각 엔드포인트마다 적용되는 관문의 부분집합만 다르다(예: GET 계열은 body가 없어 JSON 파싱 관문이 없음).

1엔드포인트 9종의 지형 — 창구 안내판

1층. 관리사무소에는 창구가 9개 있는데, 나란히 늘어선 똑같은 창구가 아니다. 어떤 창구는 보기만 하고(읽기 전용), 어떤 창구는 서류를 새로 만들거나 바꾼다(상태 변경). 그리고 딱 하나, 서명 도장 없이도 들여보내 주는 예외 창구가 있다.

읽기 전용 — 보기만 한다
상태 변경 — 서류를 만들거나 바꾼다
인증 필요
라우트 등록 순서 예외 — 인증 미들웨어보다 먼저 등록되어, 서명 없이도 통과한다(§4 참고)
2층 · 기술 상세왜 안내판이 이렇게 나뉘는가

엔드포인트민원 창구 하나하나 — 어떤 창구는 접수만, 어떤 창구는 서류를 새로 만들어 준다 9종: GET /healthz, POST /deploy, POST /projects, DELETE /projects/:name, GET /status, GET /status/:project, GET /logs/:project, POST /rollback/:project, PUT /env/:project. 인증 적용 범위는 GET /healthz를 제외한 전 라우트이며, 예외는 인증 미들웨어안내데스크를 지나야 안쪽 사무실로 들어갈 수 있는 것처럼, 모든 요청이 공통으로 거치는 검문 절차(app.use('*', ...))보다 /healthz 라우트가 먼저 등록되어 있기 때문이다(자세한 파이프라인은 §3).

근거: 04-API-명세서.md § 공통 사항 > 인증

2서명 규칙 — 문자열 조립 도해

1층. 접수증에 찍는 도장(HMAC 서명)우리 둘만 아는 인주로 찍은 도장 — 도장 모양이 같아야 진짜 접수증으로 인정된다은 아무 곳에나 찍는 게 아니다. 접수 시각과 서류 내용물을 이어붙인 종이 위에 찍는다. 내용물이 없는 서류(보기만 하는 요청)는 빈 종이에 시각만 적어 도장을 찍는다.

2층 · 기술 상세서명 생성/검증 함수 원문 
export function signPayload(body: string, timestampMs: number, secret: string): string {
  return createHmac('sha256', secret).update(`${timestampMs}.${body}`).digest('hex');
}

GET/DELETE 요청은 ['GET','DELETE'].includes(c.req.method) ? '' : await c.req.text() 로 본문(페이로드)봉투 속에 든 서류 내용물을 빈 문자열로 취급한 뒤 서명한다. 허용 오차 기본값은 maxSkewMs = 300_000ms(5분). 실패 시 401 {"error":"invalid signature"}.

근거: packages/deployer/src/hmac.ts, 04-API-명세서.md § 공통 사항 > 인증

3/healthz 인증 예외 — 등록 순서 파이프라인

1층. 안내데스크(인증 검문)는 창구를 지키고 서 있지만, 딱 하나의 창구는 안내데스크가 서기 전에 이미 열려 있었다. 그래서 그 창구로 가는 손님만 검문 없이 바로 들어간다 — 규칙이 아니라 순서 때문에 생긴 예외다.

2층 · 기술 상세등록 순서가 곧 예외인 이유

Hono 라우터는 요청마다 등록된 순서대로 라우트/미들웨어를 검사한다. app.get('/healthz', ...)가 인증 미들웨어(app.use('*', ...))보다 먼저 등록돼 있으므로, /healthz 요청은 인증 미들웨어에 닿기도 전에 이미 처리·응답이 끝난다. 이건 URL 패턴으로 예외를 뚫어준 게 아니라 등록 순서로 만들어진 의도된 예외다 — 흔히 놓치는 설계 사실이라 반드시 그림으로 남긴다.

근거: 04-API-명세서.md § 공통 사항 > 인증 (라우트 등록 순서에 의존하는 의도된 예외)

4상태코드 판정 규칙 — 결과값 → HTTP 코드 매핑

1층. 창구가 서류를 다 처리한 뒤에도 도장이 하나 더 남아있다 — 그 서류의 처리 결과가 접수증 겉면의 합격/불합격 도장으로 바뀌는 규칙이다.

2층 · 기술 상세404는 오직 한 곳에서만

404는 시리즈 전체에서 GET /status/:project 프로젝트 미존재 한 곳에서만 등장한다. DELETE /projects/:name은 등록되지 않은 이름이어도 404를 내지 않고 200을 반환한다(§7 정확성 함정 참고) — 같은 "존재하지 않는 프로젝트"인데 라우트에 따라 정반대로 처리된다는 점에 주의.

5이 창구에서 쓰는 검증 자(잣대) 3종

1층. 서식 칸에 아무 글자나 써도 되는 게 아니다. 세 가지 자로 칸의 모양을 잰다 — 이름칸, 도메인칸, 환경변수 키칸. (각 자의 눈금 하나하나를 뜯어보는 건 03번 상세 설계서의 몫이고, 여기서는 어느 창구에서 어떤 자를 쓰는지만 본다.)

PROJECT_NAME_RE

/^[a-z0-9][a-z0-9-]{0,62}$/
my-app ✓My_App ✕

적용: deploy/project/DELETE:name/status:project/logs:project/rollback:project/env:project — 사실상 전 라우트의 프로젝트명 칸

HOSTNAME_RE

/^(?={1,253})(...)(\.(...))+$/i
my-app.example.com ✓my app ✕

적용: POST /projects의 domain — 미지정 시 ${name}.${baseDomain}으로 만든 값도 다시 이 자로 잰다

ENV_KEY_RE

/^[A-Za-z_][A-Za-z0-9_]*$/
API_KEY ✓1KEY ✕

적용: PUT /env/:project의 set 객체 키. 값 자체는 정규식이 아니라 개행 문자(\r/\n) 포함 여부만 확인

2층 · 기술 상세정규식과 03번 문서의 관계

이 세 자 중 PROJECT_NAME_RE는 CLI 쪽에서도 문자열 원문까지 동일하게 정의돼 있어야 한다(03번 문서에서 다룸). 여기서는 각 잣대가 이 창구 안 어디에 쓰이는지만 지도로 보여준다 — 정규식 조각을 쪼개 각 부분이 무엇을 허용/거부하는지 해부하는 것은 03번의 시각물이다.

근거: 04-API-명세서.md § 공통 사항 (프로젝트명/도메인/env 키 검증 정규식)

6POST /projects 서식 — 틀려도 반려되지 않는 칸들

1층. 대부분의 칸은 규격이 어긋나면 반려 도장을 찍지만, 이 서식의 세 칸은 다르다. 칸을 비뚤게 써도 접수 담당자가 알아서 표준 값으로 고쳐 적고 그냥 접수해 준다.

{
  "name": "my-app",          ← PROJECT_NAME_RE, 틀리면 400 반려
  "imageRepo": "ghcr.io/owner/my-app",  ← 빈 문자열이면 400 반려
  "branch": "main",          ← string 아니면 에러 없이 'main'으로 대체
  "containerPort": 3000,     ← number 아니면 에러 없이 3000으로 대체
  "healthPath": "/",         ← string 아니면 에러 없이 '/'로 대체
  "domain": "my-app.example.com" ← 미지정시 생성 후에도 HOSTNAME_RE로 검증, 틀리면 400
}
주의동작은 upsertProject — 같은 name이 이미 있으면 새로 만들지 않고 덮어쓴다(upsert)이미 있는 세대 카드면 내용을 고쳐 쓰고, 없으면 새로 만드는 접수 방식(ON CONFLICT(name) DO UPDATE).
2층 · 기술 상세왜 이 셋만 관대한가

원문은 branch/containerPort/healthPath를 "선택, 타입 아니면 기본값으로 대체(에러 아님)"이라고 명시한다. name·imageRepo·domain은 형식 오류 시 그대로 400을 낸다는 점에서 이 셋과 대조된다 — 서식 필드마다 엄격도가 다르다는 사실 자체가 이 문서의 정확성 함정 중 하나다.

근거: 04-API-명세서.md § POST /projects > 필드별 규칙

7PUT /env/:project — 환경변수 서식 접수 절차

1층. 이 창구만 장부(DB)가 아니라 종이 파일에 바로 적는다. 접수 순서가 있다 — 폴더를 만들고, 기존 내용을 읽고, 고칠 것을 반영하고, 지울 것을 지운 뒤, 전체를 다시 써서 잠근다.

1

폴더 준비

mkdirSync(envDir, { recursive: true })

2

기존 서식 읽기

파일이 있으면 줄 단위 KEY=VALUE로 파싱해 Map으로 올림(빈 줄·# 시작 줄 제외)

3

set 반영

키는 ENV_KEY_RE 검증, 값은 개행 문자 포함 시 400

4

remove 반영

존재 여부 확인 없이 무조건 삭제 시도

5

전체 재작성 + 권한 강제

mode 0600으로 새로 쓰고, 기존 파일이었다면 chmodSync로 0600을 다시 강제(신규 생성 시에만 mode 옵션이 적용되므로)

2층 · 기술 상세왜 DB가 아니라 파일인가

PUT /env/:project는 <envDir>/<project>.env 파일을 직접 조작한다 — projects/deployments 테이블은 건드리지 않는다(테이블 접근 여부는 05번 DB 설계서의 접근 매트릭스에서 "무접근"으로 표시됨). 파일 경로의 컨테이너 내부/NAS 실제 위치 대응은 05번 문서에서 자세히 다룬다.

근거: 04-API-명세서.md § PUT /env/:project

8엔드포인트 9종 상세 서류철

1층. 위 왕복도가 어떻게 판정하는지 보여줬다면, 여기는 각 창구의 정본 규정이다 — 표로 남겨도 되는 항목들. 창구 이름 뒤에 붙는 :project 같은 칸은 경로 변수(path param)봉투 겉면 주소칸에 직접 적어 넣는 값 — URL 경로 자체의 일부, ?tail=처럼 물음표 뒤에 붙는 칸은 질의 변수(query param)주소 옆에 덧붙이는 선택 메모 — 없어도 기본값으로 처리된다다. GET /logs/:project만 정해진 JSON 서식이 아니라 text/plain 응답정해진 서식 칸이 아니라 편지지 그대로 돌려주는 응답으로 돌아온다.

9이 문서가 말하지 않는 것

1층. 창구 규정집에 없는 항목은 "없다"고 우기지 않고, "이 원문은 답하지 않는다"고 빈 도장칸으로 남긴다.

빈 도장칸

요청 빈도 제한(rate limit) — 원문에 언급 없음

빈 도장칸

CORS 정책 — 원문에 언급 없음

빈 도장칸

API 버전 관리 — 엔드포인트에 버전 프리픽스 없음, 언급 없음

빈 도장칸

사람 사용자용 로그인/세션 — 없음. 인증은 기기 간 HMAC 서명뿐

빈 도장칸

요청 크기 제한 — 원문에 언급 없음

이 다섯 칸은 "곧 될 것"이 아니라 이 문서(원문)가 다루지 않는 질문이다. 확인되지 않은 것을 확인된 것처럼 채우지 않는다 — 01번 문서의 미구현 3건, 07번 문서의 잔여 위험 4건과 같은 원칙.

07. 보안 설계서

택배 접수증의 도장과 시각우리 둘만 아는 인주로 찍은 도장(서명) + 접수 시각 — 둘 다 맞아야 창구가 받아 준다이 이 문서의 뼈대다. 이 도장의 정체가 HMAC비밀키를 섞어 계산한, 위조하기 어려운 디지털 도장 — 흔히 "서명"이라고 부른다이다. 도장이 다르거나 시각이 5분 넘게 어긋나면 창구에서 그냥 반려한다 — 무엇이 이 시스템을 지키고, 무엇은 아직 지키지 못하는지 숨김없이 적는다.

대상: @hoster/deployer (NAS 상주 API), @hoster/cli (로컬 운영 CLI) 버전 1.0 작성일 2026-08-13 원문: docs/deliverables/07-보안-설계서.md
지금 보고 있는 곳: 단지 배치도(02번 문서 자산의 축약판) 위에 신뢰 경계선을 겹친 것. 관리사무소(deployer)로 들어오는 모든 화살표는 도장(HMAC) 관문을 지나야 하고, NAS 담장 안쪽 전체가 SSH 접속·소켓 마운트관리사무소 컨테이너 안에 NAS 전체를 조종하는 리모컨(docker.sock)을 통째로 넣어 준 것 — 그 컨테이너가 뚫리면 NAS 전체가 뚫린다이라는 별도 경계다.

1신뢰 경계 4개 — 어디로 들어오고 어디서 막는가

1층. 신뢰 경계"여기서부터는 남이 보낸 것일 수 있다"고 가정하고 반드시 확인하는 선 — 관리사무소의 접수 창구 같은 것 4개가 있다. 넷 다 관리사무소(deployer)로 이어지지만, 들어오는 입력의 성격과 막는 방법이 다르다.

시그니처도장 실습기 — 손으로 확인하는 HMAC

1층. 아래 서식에서 본문·비밀키·시각 오차를 직접 바꿔 보라. 관리사무소(NAS)가 실제로 갖고 있는 열쇠는 왼쪽 아래 고정칸에 적혀 있다 — 손님이 보내는 열쇠가 이것과 다르면, 또는 접수 시각이 5분 넘게 어긋나면, 서명이 아무리 그럴듯해도 반려 도장이 찍힌다.

비밀키를 한 글자만 바꿔도, 본문을 한 글자만 바꿔도 서명 값이 완전히 달라진다. 시각 오차를 5분(±5) 밖으로 옮기면 서명이 맞아도 반려된다 — 이렇게 시각을 못박아 두는 이유가 재전송(replay) 공격과거에 도청한 진짜 접수증을 나중에 그대로 다시 접수처에 들이미는 수법 — 오래된 접수 시각이면 도장이 맞아도 반려해 막는다 방지다.

2층 · 기술 상세서명 생성/검증 함수 원문 
// packages/deployer/src/hmac.ts:3-4, packages/cli/src/hmac.ts:3-4 (동일 로직 독립 구현)
export function signPayload(body: string, timestampMs: number, secret: string): string {
  return createHmac('sha256', secret).update(`${timestampMs}.${body}`).digest('hex');
}

검증(hmac.ts:7-29): ① Number.isFinite(timestampMs) 아니면 즉시 실패 → ② Math.abs(nowMs - timestampMs) > maxSkewMs(기본 300_000ms = 5분) 이면 실패 → ③ 서명 hex 파싱 실패 시 예외 없이 false 반환 → ④ 길이 비교 후 timingSafeEqual(원리는 §3). 시크릿 생성은 randomBytes(32).toString('hex')(256비트 엔트로피, commands/init.ts:308-309).

근거: 07-보안-설계서.md § 3. 인증 설계(HMAC-SHA256)

2왜 timingSafeEqual인가

1층. 일반 문자열 비교는 앞에서 몇 글자가 맞았는지에 따라 걸리는 시간이 미묘하게 달라진다 — 공격자가 이 시간차를 반복 관찰하면 한 글자씩 정답을 알아낼 수 있다(타이밍 공격비교에 걸리는 시간의 미세한 차이를 반복 측정해 정답을 한 글자씩 추측해 내는 공격). 상수 시간 비교정답과 몇 글자가 같든 항상 똑같은 시간이 걸리게 만든 비교 방식는 몇 글자가 맞든 항상 같은 시간이 걸리게 만들어 이 정보 유출을 막는다.

길이 체크가 먼저 오는 이유 — 순서가 있는 3단계

1층. Node의 timingSafeEqual은 두 버퍼의 길이가 다르면 예외를 던진다. 그래서 상수 시간 비교를 호출하기 전에 길이부터 맞춰 봐야 한다 — 순서를 지키지 않으면 프로그램이 죽는다.

2층 · 기술 상세hmac.ts 검증 함수 순서

순서는 ① Number.isFinite(timestampMs) 확인 → ② 시각 오차(5분) 확인 → ③ hex 파싱 시도 → ④ 길이 비교 → ⑤ timingSafeEqual. 셋째~다섯째가 위 3단계 시퀀스에 해당한다.

근거: 07-보안-설계서.md § 3. 인증 설계, packages/deployer/src/hmac.ts:7-29

3입력 검증 관문 7종 — 막지 않으면 무슨 일이 나는가

1층. 정규식 원문 해부는 03·06번 문서의 몫이다. 여기서는 이 관문을 안 막으면 실제로 무슨 사고가 나는가에 집중한다 — 이를테면 경로 순회지정된 서랍 밖으로 나가는 이름("../../다른서랍")을 넣어, 원래는 못 여는 다른 파일을 열게 만드는 수법나 인젝션서식 칸에 값이 아니라 명령·코드를 몰래 끼워 넣어 시스템이 그걸 실행하게 만드는 수법(셸 명령·YAML·.env 파일 등에 끼워 넣는 형태가 있다) 같은 것이다. 원문 표는 8행이지만 마지막 행은 관문이 아니라 에러 메시지 판별용 휴리스틱이다 — 아래에서 점선으로 따로 표시했다.

4시크릿의 일생 — 생성부터 비노출까지

1층. 도장의 인주(비밀키)가 태어날 때부터 엔트로피얼마나 무작위(예측 불가능)한지를 나타내는 값 — 256비트면 찍을 수 있는 도장 모양의 경우의 수가 사실상 무한대에 가깝다 256비트짜리 난수로 만들어져, 어디에 파일 권한 0600이 서랍(파일)은 나(소유자)만 열어 볼 수 있고 남은 아예 못 연다는 잠금 표시으로 보관되고, 어떻게 건네지고, 왜 로그에 안 새는지 — 네 구간을 따라간다.

2층 · 기술 상세저장 경로·전달 코드 원문

  • deployer .env(프로젝트별, PUT /env): writeFileSync(..., { mode: 0o600 }) 후 chmodSync(file, 0o600)로 재강제(app.ts:170-177)
  • CLI 설정(~/.hoster/config.json): writeFileSync(..., { mode: 0o600 }) + chmodSync(config.ts:25-31)

잔여 위험 4건 — 아직 도장이 안 찍힌 칸

1층. 아래 넷은 "고쳤다"가 아니라 "아직 못 고쳤다, 또는 구조적으로 남는다"고 원문이 그대로 인정하는 항목이다. 축소하거나 미화하지 않는다.

잔여 위험

HMAC 시크릿 단일 공유 — CLI 로컬 설정과 각 레포의 HOSTER_DEPLOY_SECRET이 같은 값. 저장소 하나 유출이 전체 deployer API 위조로 이어짐

잔여 위험

docker.sock 마운트 — deployer 컨테이너에 rw로 마운트. 사실상 NAS 호스트의 root 권한과 동급

잔여 위험

컨테이너 root 실행 — deployer Dockerfile에 USER 지정 없음. 기본 root로 실행됨

잔여 위험

터널 충돌 정규식 휴리스틱 — Cloudflare 응답 문구가 비공식이라 관찰 기반으로 좁게 매치. 오탐·미탐 가능성이 정규식 특성상 완전히 배제되지 않음

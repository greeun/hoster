## 1. 사전 요구사항

| 구분 | 항목 | 확인/조건 |
|---|---|---|
| 로컬(Mac) | Node.js 22 | `node -v` |
| 로컬(Mac) | pnpm (workspace) | `pnpm -v` |
| 로컬(Mac) | Docker + buildx | `docker buildx version` — deployer 이미지를 `linux/amd64`로 빌드해 NAS로 전송하는 용도 (NAS 자체에서는 빌드하지 않음) |
| 로컬(Mac) | GitHub CLI(`gh`) 인증 | `gh auth status` — `hoster add`의 레포 시크릿 설정(`gh secret set`)에 사용 |
| NAS | SSH 접속 | 포트 `2222`, 키 인증. **2022 포트는 배너만 응답하고 접속 불가** — 2222가 실제 포트 |
| NAS | sudo docker NOPASSWD | `sudo -n /usr/local/bin/docker` — docker 바이너리 실행만 NOPASSWD로 허용된 상태여야 함 |
| NAS | Container Manager | 설치 상태 (docker compose 플러그인 포함) |
| 외부 | Cloudflare API 토큰 | `Zone.DNS Edit` + `Account.Cloudflare Tunnel Edit` 스코프 2종, Account ID/Zone ID 별도 확인 |
| 외부 | GitHub PAT | `read:packages` 권한 — NAS deployer가 ghcr.io private 이미지를 pull할 때 사용 (레포별 CI의 `GITHUB_TOKEN`과는 별개) |

- NAS 접속 정보는 CLI 옵션으로 변경할 수 없음 — `packages/cli/src/config.ts`의 `defaultNas()`가 `HOSTER_NAS_HOST` / `HOSTER_NAS_PORT` / `HOSTER_NAS_USER` 환경변수를 읽고, 미지정 시 예시값 `{ host: '192.168.1.100', port: 22, user: 'admin' }`을 사용함. `hoster init` 실행 전 아래처럼 실제 NAS 값을 지정할 것.

  ```bash
  export HOSTER_NAS_HOST=<NAS IP 또는 호스트명>
  export HOSTER_NAS_PORT=<SSH 포트>
  export HOSTER_NAS_USER=<SSH 계정>
  ```

  `hoster init`이 끝나면 이 값이 `~/.hoster/config.json`에 저장되므로 이후 명령에서는 환경변수가 필요 없음.
- SFTP/SCP는 비활성화 — 파일 전송은 tar over ssh로만 동작 (`nas.ts`의 `transferDir`).

## 2. 사전 점검

- **NAS 아키텍처 확인 (필수, init 실행 전)** — deployer 이미지는 `linux/amd64`로 고정 빌드됨:
  ```
  ssh -p 2222 admin@192.168.1.100 'uname -m'
  ```
  → `x86_64`(또는 호환) 확인. 다른 아키텍처(ARM 등)이면 init 진행 불가.

- SSH/docker 권한 확인 (`planInit()` 1단계와 동일 명령, 사전 실행 가능):
  ```
  ssh -p 2222 admin@192.168.1.100 'sudo -n /usr/local/bin/docker version --format {{.Server.Version}}'
  ```

- docker compose 플러그인 확인 (2단계와 동일):
  ```
  ssh -p 2222 admin@192.168.1.100 'sudo -n /usr/local/bin/docker compose version'
  ```

## 3. 설치 절차 — `hoster init` (12단계)

`hoster init --dry-run --stack-dir stack/`로 실행 전 계획만 출력 가능 (`--stack-dir` 기본값 `stack/`).

프롬프트 입력 순서: 기본 도메인 → Cloudflare API 토큰 → Cloudflare Account ID → Cloudflare Zone ID → GHCR PAT (`HMAC_SECRET`은 자동 생성, 입력 없음).

| # | 종류 | 단계 | 실패 시 증상 | 복구 |
|---|---|---|---|---|
| 1 | local-exec | NAS 접속 및 docker 권한 사전 점검 | ssh 실패, sudo 권한 없음 | SSH 키/포트(2222)/`sudo -n` NOPASSWD 설정 재확인 |
| 2 | nas-exec | docker compose 플러그인 확인 | Container Manager 미설치/구버전 | DSM에서 Container Manager 설치·업데이트 |
| 3 | cf-api | Cloudflare 터널 `hoster` 생성 | `already exists`/`duplicate` 패턴 매치 시 전용 안내문 발생 | 아래 "터널 이름 충돌" 절 참고 |
| 4 | cf-api | 터널 인그레스 설정 (`hoster.<domain>` → deployer, `*.<domain>` → traefik) | Cloudflare API 원본 오류 그대로 노출 | 토큰의 `Account.Cloudflare Tunnel Edit` 스코프 확인 |
| 5 | cf-api | DNS CNAME 설정 (`hoster.<domain>` → `<터널ID>.cfargotunnel.com`) | Cloudflare API 원본 오류 그대로 노출 | 토큰의 `Zone.DNS Edit` 스코프, Zone ID 확인 |
| 6 | nas-exec | `hoster-net` docker 네트워크 생성 | 없음 (이미 존재 시 `hoster-net 네트워크가 이미 존재합니다 — 무시합니다.` 로그만 출력하고 계속) | 조치 불필요 |
| 7 | nas-transfer | 상태 디렉터리(`/volume1/docker/hoster/state/env`) 준비 + `stack/` 전송(tar over ssh) | ssh/tar 실패 | 네트워크·NAS 디스크 여유 확인 후 재실행 |
| 8 | local-exec | deployer 이미지 buildx 빌드(`linux/amd64`) 후 NAS 전송 | 로컬 buildx 실패 또는 전송 실패 | `docker buildx version` 확인 후 재실행 |
| 9 | nas-exec | `.env` 작성(0600, `TUNNEL_TOKEN`/`HMAC_SECRET`/`GHCR_PAT`/`BASE_DOMAIN`) + `docker compose up -d` | compose up 실패 | NAS에서 `docker compose logs`로 원인 확인 |
| 10 | write-config | `~/.hoster/config.json` 저장(0600) | 거의 실패하지 않음 | — |
| 11 | nas-exec | `hoster-net` 외부 통신 진단 (`wget -T 10 https://one.one.one.one`) | **실패해도 init은 경고만 출력하고 계속 진행 — 무시 가능한 실패 아님.** cloudflared 자체가 hoster-net에서 Cloudflare로 나가는 외부 통신이 필요하므로, 이 진단 실패 시 12단계 healthz도 반드시 실패함 | DSM 방화벽/IP forward 설정 확인 (아래 "장애 대응" 참고) |
| 12 | local-exec | 터널 경유 `https://hoster.<domain>/healthz` 확인 (10초 간격 최대 6회 재시도) | `healthz 확인 실패 (6회 재시도): ...` | DNS 전파 대기 후 `curl`만 재실행, 또는 NAS `docker compose logs`로 원인 확인. **config는 10단계에서 이미 저장됐으므로 init을 처음부터 재시도할 필요 없음** |

### 3.1. 터널 이름 충돌 → `--reuse-tunnel`

- 재시도 시 `이미 'hoster' 터널이 존재합니다. Cloudflare 대시보드(Zero Trust > Networks > Tunnels)에서 기존 터널을 삭제한 뒤 다시 실행하거나, hoster init --reuse-tunnel <터널ID>로 기존 터널을 재사용하세요.` 오류 발생
- 조치 A: Cloudflare 대시보드에서 기존 `hoster` 터널 삭제 후 `hoster init` 재실행
- 조치 B: `hoster init --reuse-tunnel <터널ID>` — 새 터널을 만들지 않고 기존 터널의 토큰을 재조회해 사용

### 3.2. healthz 실패 시 — config는 이미 저장됨

- 10단계(`write-config`)는 11~12단계(네트워크 진단/healthz)보다 **먼저** 실행됨 — 이후 실패해도 로컬 설정 저장을 막지 않음
- 실패 시 CLI가 진행 상태를 안내(`printRecoveryNote`, 도달한 단계만 출력):
  ```
  중단됨 — 현재 상태:
    - /volume1/docker/hoster 에 stack 디렉터리가 이미 전송되었습니다.
    - .env 파일이 이미 작성되었습니다 (HMAC_SECRET 포함).
    재시도하면 HMAC_SECRET이 새로 생성됩니다. 이미 등록된 프로젝트가 있다면 해당
    GitHub 저장소의 HOSTER_DEPLOY_SECRET을 새 값으로 갱신하거나, 재시도 전 NAS의
    /volume1/docker/hoster 디렉터리를 제거한 뒤 다시 실행하세요.
    - ~/.hoster/config.json 파일이 이미 저장되었습니다 — 터널/DNS/.env 설치는
    대부분 완료된 상태이며, 이 설정을 재시도 없이 그대로 사용할 수 있습니다.
    DNS 전파를 기다렸다가 curl https://hoster.<baseDomain>/healthz로 다시 확인하거나,
    계속 실패하면 NAS에서 docker compose logs로 원인을 확인하세요.
  ```
- 즉 config가 저장된 이후의 실패는 **`hoster init` 재실행이 아니라** `curl` 재확인 또는 NAS 로그 확인으로 대응

### 3.3. 재실행 시 주의 — `HMAC_SECRET` 재생성

- `hoster init`을 재실행하면 새 `HMAC_SECRET`이 생성되어 NAS `.env`와 `~/.hoster/config.json`에 반영됨
- 이미 `hoster add`로 등록된 레포의 GitHub 시크릿 `HOSTER_DEPLOY_SECRET`은 이전 값 그대로 남아 서명 검증 실패(401 `invalid signature`)로 이어짐
- 조치: 재실행 후 등록된 레포마다 `hoster add`(또는 수동 `gh secret set HOSTER_DEPLOY_SECRET`)로 시크릿 재동기화

## 4. NAS 스택 운영

- compose 파일 위치: `/volume1/docker/hoster` (`docker-compose.yml`, `.env` 모두 이 디렉터리)
- 컨테이너 3종 확인:
  ```
  ssh -p 2222 admin@192.168.1.100 'sudo -n /usr/local/bin/docker ps'
  ```
  `hoster-cloudflared`, `hoster-traefik`, `hoster-deployer` 3개 모두 `Up` 상태여야 정상
- 로그 확인 (compose 기준):
  ```
  cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose logs -f [cloudflared|traefik|deployer]
  ```
  앱 컨테이너 로그는 NAS에 직접 접속하지 않고 로컬에서 `hoster logs <project> [--tail <n>]`로 조회 가능(기본 tail 200)
- 전체 재기동:
  ```
  cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose --env-file .env up -d
  ```
- 개별 컨테이너 재시작:
  ```
  sudo -n /usr/local/bin/docker restart hoster-<cloudflared|traefik|deployer>
  ```
- 세 컨테이너 모두 `restart: unless-stopped` — NAS 재부팅 시 자동 복구, 상태(SQLite)는 볼륨 마운트로 영속

## 5. 장애 대응

| 증상 | 원인 | 조치 |
|---|---|---|
| `hoster-net`(docker bridge)에서 외부 통신 불가 | 과거 이력 있음 — DSM 방화벽/IP forward 설정 문제. `hoster-cloudflared`가 이 네트워크 위에서 Cloudflare로 나가는 외부 통신이 반드시 필요함 | `hoster doctor`로 진단 재실행(`wget -T 10 https://one.one.one.one` 동일 명령). DSM 방화벽/IP forward 설정 확인. 해결 전까지 터널 연결 불가 → 모든 배포/healthz 실패 |
| 배포가 계속 실패하고 `hoster-<project>-old` 컨테이너가 잔존 | 구버전 deployer: swap 실패 시 정리 호출이 Docker 304(already stopped)에서 예외를 던져 롤백 로직이 중단됨 | 최신 deployer 이미지로 업그레이드(6절). `docker.ts`의 `ignoreAlreadyInTargetState`가 404/304를 모두 무시하도록 수정되어 해소됨(커밋 `2e04ed1`, `b72a15d`). 잔존 컨테이너는 `docker ps -a --filter name=-old`로 확인 후 수동 정리 |
| 터널 다운 (모든 프로젝트 도메인 무응답, `/healthz` 실패) | `hoster-cloudflared` 컨테이너 장애 또는 `hoster-net` 외부 통신 문제 | `docker ps`로 `hoster-cloudflared` Up 여부 확인. `restart: unless-stopped`로 평시 자동 복구되나, 안 되면 `docker compose up -d`. Cloudflare 대시보드(Zero Trust > Networks > Tunnels)에서 터널 상태 확인 |
| deployer 다운 (CLI 전 커맨드 실패, `/deploy` 타임아웃) | `hoster-deployer` 컨테이너 장애 | `docker ps`로 확인 → `docker compose up -d`로 재기동. `docker compose logs deployer`로 원인 확인. 401 `invalid signature` 응답이면 시크릿 불일치(3.3절) 확인, 타임스탬프 허용 오차는 5분(`hmac.ts` `maxSkewMs=300_000`) |
| `hoster init` 재시도 시 터널 이름 충돌 | `hoster` 터널이 Cloudflare에 이미 존재 | 3.1절 참고 (`--reuse-tunnel` 또는 대시보드에서 삭제) |

## 6. 백업·복구

- state 디렉터리: `/volume1/docker/hoster/state` (NAS), `docker-compose.yml`에서 `/volume1/docker/hoster/state:/state`로 deployer 컨테이너에 마운트
- 백업 대상:
  - `/volume1/docker/hoster/state/hoster.db` — 프로젝트 등록 정보, 배포 이력, 현재/직전 이미지 (better-sqlite3, WAL 모드)
  - `/volume1/docker/hoster/state/env/*.env` — 프로젝트별 환경변수 (0600)
  - `/volume1/docker/hoster/.env` — `TUNNEL_TOKEN`/`HMAC_SECRET`/`GHCR_PAT`/`BASE_DOMAIN` (0600)
  - 로컬 `~/.hoster/config.json` (Mac, 0600) — NAS 접속정보, Cloudflare 인증정보, `hmacSecret`, `ghcrPat`
- 방법: DSM 표준 백업 도구(Hyper Backup 등)로 `/volume1/docker/hoster` 디렉터리 전체 포함. `~/.hoster/config.json`은 시크릿을 포함하므로 별도로 안전하게 보관(암호화 저장 권장)
- 복구: `.env`와 `state/`를 동일 경로로 복원 후 `docker compose --env-file .env up -d`. `~/.hoster/config.json` 복원 전에는 로컬 CLI가 `설정 파일이 없습니다 (...). hoster init을 먼저 실행하세요.` 오류로 즉시 종료됨

## 7. 업그레이드 (deployer 이미지 재빌드·재전송)

3절 8단계와 동일한 명령을 그대로 재사용:

```
docker buildx build --platform linux/amd64 \
  -f packages/deployer/Dockerfile -t hoster-deployer:latest --load .

docker save hoster-deployer:latest | gzip | \
  ssh -p 2222 admin@192.168.1.100 'gunzip | sudo -n /usr/local/bin/docker load'
```

NAS에서 컨테이너 재기동:

```
cd /volume1/docker/hoster && sudo -n /usr/local/bin/docker compose --env-file .env up -d
```

- 이미지 태그가 `hoster-deployer:latest`로 고정이므로 `docker load` 직후 `up -d`가 새 이미지로 재기동함
- `state/`(hoster.db, env/)는 볼륨 마운트이므로 컨테이너 재기동과 무관하게 보존됨
- **업그레이드 목적으로 `hoster init` 전체를 재실행하지 말 것** — `HMAC_SECRET`이 재생성되어 기존 레포 시크릿과 불일치 발생(3.3절). 업그레이드는 위 이미지 재빌드/전송 + `compose up`만 수동 반복

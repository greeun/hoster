## 1. 시작하기 — 신규 Next.js 프로젝트 등록

1. Next.js 프로젝트 생성:
   ```
   npx create-next-app@latest my-app
   cd my-app
   ```
2. `next.config.ts`(또는 `.js`/`.mjs`/`.cjs`)에 `output: 'standalone'` 추가.
   - 미설정 시 `hoster add`가 Dockerfile 자동 생성 단계에서 경고 출력: `next.config에 output: 'standalone' 설정이 없습니다 — 추가가 필요합니다.`
3. GitHub 레포 생성 후 push (예: `gh repo create <owner>/my-app --private --source=. --push`)
4. 레포 루트에서 등록:
   ```
   hoster add
   ```
   생성/설정되는 것:
   - `Dockerfile` — 이미 있으면 건너뜀, 없고 Next.js면 `templates/Dockerfile.nextjs.tpl`로 자동 생성
   - `.github/workflows/hoster-deploy.yml` — 이미 있으면 건너뜀(`--force`로 덮어쓰기 가능)
   - GitHub 레포 시크릿 `HOSTER_DEPLOY_URL`, `HOSTER_DEPLOY_SECRET` (`gh secret set`)
   - Cloudflare DNS CNAME `<project>.<baseDomain>`
   - deployer에 프로젝트 등록
5. 생성 파일 커밋 및 push:
   ```
   git add Dockerfile .github && git commit -m "chore: hoster add" && git push
   ```
   이 push가 GitHub Actions를 트리거해 최초 배포가 시작됨. `hoster add` 완료 시 동일한 안내가 출력됨: `커밋 후 push하면 배포됩니다: git add Dockerfile .github && git commit && git push`
6. 도메인 확인:
   ```
   curl https://<project>.<baseDomain>
   ```
   `hoster ls`로 등록된 프로젝트명/도메인/현재 이미지(짧은 sha)를 확인 가능.

## 2. 커맨드 레퍼런스

### `hoster init`

| 항목 | 내용 |
|---|---|
| 용도 | NAS에 hoster 스택(cloudflared/traefik/deployer) 설치, Cloudflare 터널/DNS/HMAC 시크릿 구성 (1회 부트스트랩) |
| 형식 | `hoster init [옵션]` |
| 플래그 | `--dry-run`(계획만 출력), `--stack-dir <dir>`(기본 `stack/`), `--reuse-tunnel <id>`(기존 터널 재사용) |
| 출력 예 | `--dry-run: 아래 12개 작업을 실행하지 않고 계획만 표시합니다.` 이어서 `1. [local-exec] NAS 접속 및 docker 권한 사전 점검` 형태로 12줄 |
| 주의 | 재실행 시 `HMAC_SECRET`이 재생성되어 등록된 레포 전체 재동기화 필요 — 설치·운영 매뉴얼 3.3절 참고 |

### `hoster add`

| 항목 | 내용 |
|---|---|
| 용도 | 현재 디렉터리의 GitHub 레포를 hoster에 등록 |
| 형식 | `hoster add [옵션]` (레포 루트에서 실행) |
| 플래그 | `--branch <branch>`(기본 `main`), `--project <name>`(기본: 레포 이름에서 추론), `--dry-run`, `--force`(기존 workflow 파일 덮어씀) |
| 출력 예 | `1. 프로젝트 "my-app" (owner/my-app), 이미지 저장소 "ghcr.io/owner/my-app"` / `2. Next.js 감지 — Dockerfile 생성 예정 (templates/Dockerfile.nextjs.tpl)` / `3. .github/workflows/hoster-deploy.yml 생성 예정 (branch=main, project=my-app)` |
| 주의 | `gh` 미설치 시 `GitHub CLI(gh)가 설치되어 있지 않습니다. https://cli.github.com/ 에서 설치한 뒤 다시 실행하세요.`, 미인증 시 `gh CLI에 로그인되어 있지 않습니다. \`gh auth login\` 을 실행한 뒤 다시 시도하세요.` — 두 점검 모두 파일 생성 전에 먼저 수행되므로 저장소가 "반쯤 설정된" 상태로 남지 않음. 기존 workflow 파일은 `--force` 없이는 보존됨 |

### `hoster ls`

| 항목 | 내용 |
|---|---|
| 용도 | 등록된 프로젝트 목록과 현재 이미지 표시 |
| 형식 | `hoster ls` |
| 플래그 | 없음 |
| 출력 예 | `NAME     DOMAIN              IMAGE` 다음 줄에 `my-app   my-app.example.com     a1b2c3d` (이미지는 태그 뒤 7자리 sha, 없으면 `-`). 등록 프로젝트가 없으면 `등록된 프로젝트가 없습니다.` |
| 주의 | 없음 |

### `hoster status <project>`

| 항목 | 내용 |
|---|---|
| 용도 | 프로젝트 상세 정보와 최근 배포 이력(최대 20건) 표시 |
| 형식 | `hoster status <project>` |
| 플래그 | 없음 |
| 출력 예 | `이름: my-app` / `도메인: my-app.example.com` / `현재 이미지: ghcr.io/...:abc1234` / `이전 이미지: -` / `최근 배포 이력:` / `  #3  2026-08-13...  success  abc1234` |
| 주의 | 이력의 `status`는 `success`/`failed`/`rolled_back` 중 하나, 실패 시 `error=...` 접미사가 붙음 |

### `hoster logs <project>`

| 항목 | 내용 |
|---|---|
| 용도 | 컨테이너 로그 표시 |
| 형식 | `hoster logs <project> [옵션]` |
| 플래그 | `--tail <n>`(기본 200) |
| 출력 예 | 컨테이너 stdout/stderr 텍스트 그대로 |
| 주의 | 없음 |

### `hoster rollback <project>`

| 항목 | 내용 |
|---|---|
| 용도 | 직전 이미지로 롤백 |
| 형식 | `hoster rollback <project>` |
| 플래그 | 없음 |
| 출력 예 | `프로젝트 "my-app"를 이전 이미지로 롤백했습니다.` |
| 주의 | 실패 시 `롤백 실패: <deployer error 필드>` — 예: 직전 이미지가 없으면 `롤백 실패: no previous image` |

### `hoster env set` / `hoster env rm`

| 항목 | 내용 |
|---|---|
| 용도 | 프로젝트 환경변수 설정/제거 (NAS 측에만 저장, 레포에 노출 없음) |
| 형식 | `hoster env set <KEY=VALUE...> [옵션]` / `hoster env rm <KEY...> [옵션]` |
| 플래그 | `--project <name>`(기본: 현재 레포에서 추론), `--redeploy`(`set`에만 존재 — 변경 후 현재 이미지로 재배포) |
| 출력 예 | `프로젝트 "my-app"의 환경변수를 갱신했습니다.` (`--redeploy` 지정 시 추가로 `이미지 ghcr.io/...:abc1234 로 재배포를 요청했습니다 (success).`) |
| 주의 | 인자가 `KEY=VALUE` 형식이 아니면 `KEY=VAL 형식이어야 합니다: <값>`. `rm`에는 `--redeploy`가 없음 — 3절 참고 |

### `hoster remove <project>`

| 항목 | 내용 |
|---|---|
| 용도 | 프로젝트 제거 (deployer 등록/컨테이너 + DNS 레코드) |
| 형식 | `hoster remove <project>` |
| 플래그 | 없음 |
| 출력 예 | `프로젝트 "my-app"가 제거되었습니다 (deployer 등록/컨테이너 + DNS 레코드 my-app.example.com).` 이어서 `workflow 파일(.github/workflows/hoster-deploy.yml)은 자동으로 삭제되지 않습니다 — 레포에서 직접 삭제하세요.` |
| 주의 | 도메인은 `<project>.<baseDomain>` 관례로 추정하지 않고 deployer에 저장된 실제 값을 조회해 삭제 — 6절 참고 |

### `hoster doctor`

| 항목 | 내용 |
|---|---|
| 용도 | NAS 접속/docker 권한/`hoster-net` 외부 통신 상태 점검 (상태 변경 없음) |
| 형식 | `hoster doctor` |
| 플래그 | 없음 |
| 출력 예 | `점검: NAS 접속 및 docker 권한 사전 점검` / `  OK` / (반복) / `doctor: 점검 완료 (변경 사항 없음)` |
| 주의 | `~/.hoster/config.json`을 읽으므로 `hoster init` 선행 필요. 없으면 `설정 파일이 없습니다 (...). hoster init을 먼저 실행하세요.` |

## 3. 환경변수 관리

- 설정: `hoster env set KEY=VALUE [KEY2=VALUE2 ...] [--project <name>] [--redeploy]`
- 제거: `hoster env rm KEY [KEY2 ...] [--project <name>]`
- 프로젝트 미지정 시 현재 디렉터리의 git origin에서 추론 — `hoster add`가 등록 시 쓰는 것과 동일한 규칙(`parseGitHubRepo` + `projectNameOf`). 다른 디렉터리에서 관리하려면 `--project` 필수
- `--redeploy`: 변경 직후 **현재 이미지로** 재배포 트리거. `env set`에만 존재 — `env rm`에는 없으므로, 제거를 즉시 반영하려면 별도로 재배포하거나 다음 정상 배포(push)를 기다려야 함
- 저장 위치: NAS `/volume1/docker/hoster/state/env/<project>.env` (파일 권한 0600). 레포/워크플로 어디에도 값이 노출되지 않음 — 앱 환경변수는 NAS에만 존재
- 값 제약: 키는 `[A-Za-z_][A-Za-z0-9_]*` 형식만 허용, 값에 개행 문자(`\r`/`\n`) 불가 — 위반 시 서버가 `invalid env key: <key>` 또는 `invalid env value for <key>` 반환

## 4. 배포 동작 이해

push부터 반영까지:

1. `git push` (등록 시 지정한 브랜치, 기본 `main`)
2. GitHub Actions가 `docker/build-push-action`으로 이미지 빌드 → `ghcr.io/<owner>/<repo>:<sha>`, `:latest` 태그로 push
3. Actions가 `$HOSTER_DEPLOY_URL/deploy`에 POST — 본문 `{"project","image","sha"}`, 헤더 `x-hoster-timestamp`/`x-hoster-signature`(HMAC-SHA256, `${ts}.${body}`를 `HOSTER_DEPLOY_SECRET`으로 서명)
4. Cloudflare Tunnel 경유로 NAS deployer 도달 → ghcr.io pull → 기존 `hoster-<project>` 컨테이너를 `hoster-<project>-old`로 rename 후 즉시 정지 → 새 이미지로 `hoster-<project>` 기동 → 헬스체크(`http://hoster-<project>:<port><healthPath>`, 기본 60초 타임아웃·1초 간격 재시도)

**교체 중 수 초 무응답** (의도된 트레이드오프, 무중단 배포 아님):
- 원인: 기존 컨테이너를 rename 직후 정지 — Traefik이 동일 라우터에 old+new 두 백엔드를 동시에 등록하는 것을 방지
- 구간: 새 컨테이너가 헬스체크를 통과할 때까지 해당 URL 완전 무응답
- 길이: 정상 배포 수 초 / 실패 롤백 시 최대 60초(헬스체크 타임아웃)
- 목적: 검증되지 않은 새 버전으로 트래픽이 새는 것을 방지

**실패 시 자동 롤백(최대 60초)**:
- 헬스체크 실패 → 새 컨테이너 제거 → old 컨테이너를 원래 이름으로 rename 후 재시작(`start`) → 배포 이력에 `failed` 기록
- 최대 60초 뒤 서비스는 실패 이전 버전으로 자동 복귀

**연속 push 시 중간 요청 skip**:
- 같은 프로젝트에 배포 진행 중 새 배포 요청 도착 → 큐잉
- 대기 중이던 이전 배포 요청은 `skipped` 처리, 최신 요청만 실행
- rollback 요청은 skip 대상 아님 — 도착 순서대로 대기

## 5. 롤백

- 명령: `hoster rollback <project>`
- **직전 이미지로만** 롤백 가능 — deployer는 현재/직전 이미지 2개만 보관하므로 2단계 이전으로는 롤백 불가
- 직전 이미지가 없으면 실패: `롤백 실패: no previous image`
- 롤백도 배포와 동일한 swap/헬스체크 절차(4절)를 거침 — 롤백 자체가 실패하면 배포 이력에 `failed`로 기록

## 6. 프로젝트 제거

- 명령: `hoster remove <project>`
- **하는 일**: deployer에 등록된 프로젝트 정보 삭제, 실행 중인 컨테이너 정지/제거, Cloudflare DNS 레코드(관례 추정이 아닌 `hoster status`로 조회한 실제 도메인 값) 삭제
- **안 하는 일**:
  - `.github/workflows/hoster-deploy.yml` 워크플로 파일은 자동 삭제되지 않음 — 레포에서 직접 삭제해야 이후 push가 더 이상 `/deploy`를 호출하지 않음
  - GitHub 레포 시크릿(`HOSTER_DEPLOY_URL`, `HOSTER_DEPLOY_SECRET`)도 자동 삭제되지 않음 — 필요 시 `gh secret delete`로 수동 정리
- 부분 실패 시 안내: deployer 등록/컨테이너 제거가 먼저 성공한 뒤 DNS 삭제가 실패하면 `deployer 등록/컨테이너는 제거되었지만 DNS 레코드(<domain>) 삭제에 실패했습니다: ... Cloudflare 대시보드에서 직접 삭제하세요.`

## 7. 제약사항

- **브랜치명(`--branch`)**: 정규식 `^[A-Za-z0-9][A-Za-z0-9._/-]{0,199}$` — 영숫자와 `. _ / -`만 허용하는 보수적 부분집합. 추가로 `..`/`//` 포함 불가, `/`로 끝나거나 `.lock`으로 끝나면 거부. 유니코드/`+`/공백/따옴표는 거부됨 — `.github/workflows/hoster-deploy.yml` 템플릿에 YAML 문자열과 셸 이중따옴표 문자열(`printf` 안) 양쪽으로 그대로 삽입되기 때문
- **프로젝트명(`--project`)**: 정규식 `^[a-z0-9][a-z0-9-]{0,62}$` — 소문자/숫자/하이픈, 63자 이하, 첫 글자는 영숫자. CLI(`repo.ts`)와 deployer 서버(`app.ts`) 양쪽에서 동일 규칙으로 검증. 미지정 시 레포 이름에서 자동 변환(`projectNameOf`: 소문자화 → 비허용 문자를 `-`로 치환 → 연속 하이픈 축소 → 앞뒤 하이픈 제거 → 63자 초과 시 절단하고 다시 끝 하이픈 제거)
- **Dockerfile 자동 생성은 Next.js만**: `package.json`의 `dependencies`/`devDependencies`에 `next`가 있어야 자동 생성 대상. 그 외 프레임워크는 Dockerfile을 직접 작성해야 함 — 없으면 경고만 출력: `Dockerfile이 없고 Next.js 프로젝트가 아닙니다 — 직접 Dockerfile을 추가하세요.`
- **GitHub owner/repo 문자 제한**: git origin URL의 owner/repo는 `^[A-Za-z0-9._-]+$`만 허용 — 위반 시 `GitHub 원격 URL의 owner/repo에 허용되지 않는 문자가 포함되어 있습니다: <url>`

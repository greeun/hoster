## 시스템 구성도

### 배포 흐름 (앱 push → 배포)

```
[로컬 Mac]
  git push (hoster add --branch로 지정한 브랜치, 기본 main)
        │
        ▼
[GitHub Actions] (ubuntu-latest)
  actions/checkout
  → docker/setup-buildx-action
  → docker/login-action (ghcr.io, GITHUB_TOKEN)
  → docker/build-push-action
      tags: ghcr.io/<owner>/<repo>:<sha>, :latest
  → HMAC-SHA256(`${ts}.${body}`, HOSTER_DEPLOY_SECRET) 서명
  → POST https://hoster.<baseDomain>/deploy
        │  헤더: x-hoster-timestamp, x-hoster-signature
        ▼
[Cloudflare Tunnel]  hostname hoster.<baseDomain> → http://hoster-deployer:8080
        │
        ▼
┌─────────────────────────────── NAS (hoster-net) ───────────────────────────────┐
│  [hoster-deployer]                                                             │
│    HMAC 검증 → StateStore.recordDeployment(pending)                            │
│    → DockerManager.pull(ghcr.io/... , GHCR_PAT 인증)                           │
│    → hoster-<project> → hoster-<project>-old rename → stop                     │
│    → 새 이미지로 hoster-<project> 기동 (Traefik label 부착)                     │
│    → healthCheck(http://hoster-<project>:<port><healthPath>, 최대 60초)         │
│      성공: old 제거 + current/previous 이미지 갱신 + 직전-1 이미지 삭제          │
│      실패: 새 컨테이너 제거 + old rename 복구 + start + 이력 failed 기록         │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 사용자 트래픽 흐름

```
브라우저
   │  https://<project>.example.com
   ▼
[Cloudflare]  DNS(CNAME, proxied) + 엣지 HTTPS 종료
   │
   ▼
[Cloudflare Tunnel]  hostname *.<baseDomain> → http://hoster-traefik:80
   │
   ▼
┌───────────────── NAS (hoster-net) ─────────────────┐
│  [hoster-traefik]  (:80, docker provider)           │
│    label 매칭: Host(`<project>.example.com`)           │
│         │                                           │
│         ▼                                           │
│  [hoster-<project>]  (앱 컨테이너, containerPort)    │
└──────────────────────────────────────────────────────┘
```

## 네트워크 설계

- `hoster-net`: docker bridge 네트워크, `stack/docker-compose.yml`에서 `external: true`로 선언 — `hoster init` 6단계(`sudo -n /usr/local/bin/docker network create hoster-net`)가 사전 생성, compose 자체는 생성하지 않음.
- 3개 상주 컨테이너(cloudflared/traefik/deployer) + 모든 앱 컨테이너가 `hoster-net`에 참여.
- 포트 없음 원칙: `stack/docker-compose.yml`의 3개 서비스 모두 `ports:` 항목이 없음 — NAS 호스트에 노출된 포트 없이 오직 `hoster-net` 내부 통신 + Cloudflare Tunnel(아웃바운드 연결)로만 인입.
- Cloudflare Tunnel 인그레스 2규칙 (`hoster init` 4단계, `Cloudflare.setTunnelIngress`):
  - `hoster.<baseDomain>` → `http://hoster-deployer:8080`
  - `*.<baseDomain>` → `http://hoster-traefik:80`
  - 매칭 없음 → `http_status:404`
- Traefik 실행 인자: `--providers.docker=true`, `--providers.docker.exposedbydefault=false`(라벨 명시된 컨테이너만 라우팅), `--providers.docker.network=hoster-net`, `--entrypoints.web.address=:80`.
- deployer 리스닝 포트: 컨테이너 내부 8080(`PORT` env, 기본값 8080, `packages/deployer/src/index.ts`).
- 앱 컨테이너 접근 경로: Traefik → `hoster-<project>` 컨테이너명(hoster-net 내부 DNS) → `containerPort`(기본 3000). deployer 헬스체크도 동일하게 `http://hoster-<project>:<port><healthPath>` 사용.
- Cloudflare DNS: 프로젝트별 CNAME `<project>.<baseDomain>` → `<tunnelId>.cfargotunnel.com`, `proxied: true`.

## 기술 선정 사유

| 결정 항목 | 선택 | 대안 | 사유 |
|---|---|---|---|
| 이미지 빌드 위치 | GitHub Actions에서 빌드 | NAS 자체 빌드 | NAS docker bridge 네트워크에서 과거 외부 통신 불가 이력 확인됨(spec "NAS 접속 정보") — NAS 내에서 의존성 설치 등 외부 통신이 필요한 빌드 단계 수행이 곤란 |
| 외부 트래픽 인입 | Cloudflare Tunnel | 라우터 포트포워딩 | spec 확정 결정 사항: "외부 트래픽 인입 = Cloudflare Tunnel(포트포워딩 없음)" — NAS 호스트에 포트를 열지 않고도 공개 서비스 가능 |
| 프로젝트별 라우팅 | Traefik docker label 기반 | cloudflared 인그레스에 프로젝트별 규칙 직접 추가 | cloudflared 인그레스는 `hoster init` 부트스트랩 시 1회(`hoster.<domain>`→deployer, `*.<domain>`→traefik)만 설정하고 이후 변경 불필요(README) — 프로젝트 추가/삭제 시 Traefik이 컨테이너 label만 보고 자동 반영(`--providers.docker`), 터널 설정 재적용 불필요 |
| deployer 이미지 빌드·전달 | 로컬 Mac에서 `docker buildx build --platform linux/amd64 --load` 후 `docker save \| gzip \| ssh ... docker load` | NAS에서 `docker build`로 직접 빌드 | NAS bridge 네트워크 외부 통신 불가 이력으로 NAS에서 `pnpm install` 등 외부 통신이 필요한 빌드 수행이 어려움(README "deployer 이미지 빌드/배포") — `stack/docker-compose.yml`의 `deployer` 서비스에는 `build:` 섹션 없이 `image: hoster-deployer:latest`만 참조 |

## 배포 시퀀스

`POST /deploy` 수신 이후 절차(`packages/deployer/src/orchestrator.ts`, `packages/deployer/src/docker.ts`, `packages/deployer/src/app.ts` 기준):

1. Hono 미들웨어가 `x-hoster-timestamp`/`x-hoster-signature` 검증(허용 오차 5분, `timingSafeEqual`) — 실패 시 401.
2. `Orchestrator.deploy()`가 프로젝트별 큐에 등록 — 이미 실행 중인 작업이 있으면 대기, 대기 중이던 이전 deploy는 `skipped`로 즉시 resolve.
3. `StateStore.recordDeployment()`로 배포 이력 생성(status 기본 `pending`).
4. `DockerManager.pull(image)` — `GHCR_PAT` 인증으로 ghcr.io private 이미지 pull.
5. `swapContainer()`: 잔여 `hoster-<project>-old` 컨테이너를 우선 `stopAndRemove`로 정리.
6. `hoster-<project>` → `hoster-<project>-old` rename 시도(최초 배포 등 대상이 없으면 실패를 무시하고 `renamed=false`로 진행).
7. rename 성공 시 old 컨테이너를 `stop()`(제거는 아님, 롤백을 위해 보존).
8. `DockerManager.run()`으로 새 이미지의 `hoster-<project>` 컨테이너 기동 — Traefik label 자동 부착, `hoster-net` 연결, `RestartPolicy: unless-stopped`.
9. `healthCheck()` 실행: `http://hoster-<project>:<port><healthPath>`, 1초 간격 재시도, 기본 타임아웃 60초, 응답 코드 400 미만이면 통과.
10. 성공 시: old 컨테이너 `stopAndRemove`, `StateStore.setImages(current=새 이미지, previous=이전 current)`, 이전 previous(직전-1) 이미지가 새 current/previous와 다르면 `removeImage`로 삭제, 배포 이력 `success` 기록.
11. 실패 시: 새 컨테이너 `stopAndRemove`, rename됐던 경우 old를 원래 이름(`hoster-<project>`)으로 rename 후 `start()`로 재기동, 배포 이력 `failed` + 오류 메시지 기록.
12. 큐에 대기 작업이 있으면 다음 작업을 이어서 실행(`drain`).

## 컨테이너 교체 전략 (stop-before-start)

- rename만으로는 Docker 라벨이 그대로 유지되어 old 컨테이너가 새 컨테이너와 동일한 Traefik 라우터/서비스 라벨을 계속 가짐 — 실행 상태로 두면 헬스체크 대기 중(최대 60초) old+new 두 백엔드가 동시에 Traefik에 등록되어, 아직 검증되지 않은 새 버전으로도 트래픽이 흐를 수 있음.
- 이를 막기 위해 rename 직후 old 컨테이너를 즉시 `stop()`하여 Traefik 라우팅에서 제외(Traefik의 docker provider는 실행 중인 컨테이너만 반영).
- **트레이드오프**: 검증되지 않은 새 버전으로의 트래픽 유출을 막는 대신, 스왑 도중 해당 프로젝트가 짧게 완전히 응답하지 않는 구간이 발생.
  - 정상 배포: 새 컨테이너가 뜨는 수 초.
  - 헬스체크 실패로 롤백되는 경우: 최대 60초(헬스체크 타임아웃)까지 무응답.
- 롤백 경로 원복: `stopAndRemove(new)` → `rename(old→원래 이름)` → `start(원래 이름)` — old는 `stop()`으로 정지된 상태이므로 rename만으로는 복구되지 않고 반드시 `start()` 필요.
- dockerode의 404(대상 없음)/304(이미 목표 상태) 응답은 정상 상태로 간주해 무시(`DockerManager.ignoreAlreadyInTargetState`) — 특히 304는 롤백 경로에서 `stop` 실패 후에도 `start`를 호출하는데, old 컨테이너가 이미 실행 중인 경우(=진짜 데몬 오류가 "already started"로 가려지는 것을 방지)에 중요.

## 상태 관리

- SQLite 파일 위치: `/volume1/docker/hoster/state/hoster.db`(NAS 호스트 경로) — compose에서 `/volume1/docker/hoster/state:/state`로 마운트, `STATE_DIR=/state` env, `StateStore` 생성자가 `join(stateDir, 'hoster.db')` 사용.
- 저널 모드 WAL(`db.pragma('journal_mode = WAL')`).
- `projects` 테이블: `name`(PK), `image_repo`, `domain`, `branch`, `health_path`, `container_port`, `current_image`, `previous_image`.
- `deployments` 테이블: `id`, `project`, `image`, `sha`, `status`(`pending`/`success`/`failed`/`rolled_back`), `error`, `created_at` — `listDeployments`는 프로젝트별 최신순 20건 기본 조회.
- 이미지 보관 정책: 프로젝트당 현재(`current_image`) + 직전(`previous_image`) 2개만 보관 — 배포 성공 시 직전-1 이미지를 `removeImage`로 자동 삭제, 디스크 누적 방지.
- 환경변수 파일: `/volume1/docker/hoster/state/env/<project>.env`, `KEY=VAL` 형식(`#` 주석/빈 줄 무시), 파일 권한 0600(덮어쓸 때도 `chmodSync`로 강제) — `PUT /env/:project`가 갱신.

## 확인 못 해 뺀 항목

- host 네트워크 폴백 관련 아키텍처(고유 포트 자동 할당 범위 등) — 코드에 미구현이라 아키텍처 설계에서도 제외(01번 문서 "범위 제외" 참고).
- Container Manager/DSM 버전별 세부 동작 차이 — spec에 최초 확인 시점(docker 24.0.2)만 기록되어 있고 이후 버전 검증 근거 없음.

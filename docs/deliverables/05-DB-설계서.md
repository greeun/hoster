## 3. 테이블 명세

### 3.1 CREATE TABLE 원문 (store.ts:21-33)

```sql
CREATE TABLE IF NOT EXISTS projects (
  name TEXT PRIMARY KEY, image_repo TEXT NOT NULL, domain TEXT NOT NULL,
  branch TEXT NOT NULL, health_path TEXT NOT NULL, container_port INTEGER NOT NULL,
  current_image TEXT, previous_image TEXT
);
CREATE TABLE IF NOT EXISTS deployments (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project TEXT NOT NULL, image TEXT NOT NULL, sha TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending', error TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### 3.2 projects

| 컬럼 | 타입 | 제약 | 의미 |
|---|---|---|---|
| name | TEXT | PRIMARY KEY | 프로젝트명 (PROJECT_NAME_RE = `/^[a-z0-9][a-z0-9-]{0,62}$/` 준수, app.ts에서 검증) |
| image_repo | TEXT | NOT NULL | 컨테이너 이미지 저장소 경로 (예: `ghcr.io/owner/repo`) |
| domain | TEXT | NOT NULL | Traefik 라우터 Host 규칙에 쓰이는 도메인. 미지정 시 `${name}.${baseDomain}` 기본값(app.ts POST /projects) |
| branch | TEXT | NOT NULL | 배포 대상 브랜치. 미지정 시 기본 `'main'` |
| health_path | TEXT | NOT NULL | 헬스체크 경로. 미지정 시 기본 `'/'` |
| container_port | INTEGER | NOT NULL | 컨테이너 내부 리스닝 포트. 미지정 시 기본 `3000` |
| current_image | TEXT | NULL 허용 | 현재 배포된 이미지 태그. 최초 상태는 NULL(컬럼 정의에 DEFAULT 없음, upsertProject가 값을 넣지 않음) |
| previous_image | TEXT | NULL 허용 | 직전 배포 이미지 태그(롤백 대상). 최초 상태 NULL |

### 3.3 deployments

| 컬럼 | 타입 | 제약 | 의미 |
|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 배포 이력 고유 ID |
| project | TEXT | NOT NULL | 대상 프로젝트명(문자열, FK 아님) |
| image | TEXT | NOT NULL | 배포/롤백 대상 이미지 태그 |
| sha | TEXT | NOT NULL | 커밋 SHA. rollback 요청 시에는 리터럴 문자열 `'rollback'`이 저장됨(orchestrator.ts doRollback) |
| status | TEXT | NOT NULL DEFAULT `'pending'` | 배포 상태. `updateDeploymentStatus`가 허용하는 값: `'pending' \| 'success' \| 'failed' \| 'rolled_back'` |
| error | TEXT | NULL 허용 | 실패 사유 메시지. 성공 시 NULL |
| created_at | TEXT | NOT NULL DEFAULT `(datetime('now'))` | 레코드 생성 시각(UTC, SQLite `datetime('now')`) |

## 4. 관계

### 4.1 FK 없음

- `deployments.project`(TEXT)는 `projects.name`(PK)을 논리적으로 참조하나, CREATE TABLE 원문에 `FOREIGN KEY` 절 없음 — 참조 무결성이 DB 레벨에서 보장되지 않음

### 4.2 한계 (코드로 확인된 사실)

- **프로젝트 삭제 시 이력 미삭제**: `removeProject`는 `DELETE FROM projects WHERE name = ?`만 실행(store.ts:57), `deployments` 테이블에 대한 CASCADE/수동 삭제 없음 — 삭제된 프로젝트의 배포 이력 행이 고아 상태로 남음
- **미등록 프로젝트로도 deployments 행 생성 가능(deploy 경로)**: `orchestrator.execute()`는 `store.recordDeployment(req)`(orchestrator.ts:113)를 `store.getProject(req.project)` 존재 확인(orchestrator.ts:114-115)보다 **먼저** 호출함 — `POST /deploy`는 `project` 값을 정규식(PROJECT_NAME_RE) 형식만 검증하고 `projects` 테이블 존재 여부는 검증하지 않으므로, 형식은 유효하나 등록되지 않은 프로젝트명으로 요청해도 `deployments` 행이 먼저 INSERT된 뒤(`status='pending'`) `'unknown project'` 오류로 `status='failed'` 업데이트됨
- **rollback 경로는 비대칭**: `orchestrator.doRollback()`은 `store.getProject(project)` 확인(orchestrator.ts:139-141)이 `store.recordDeployment` 호출(orchestrator.ts:143)보다 **먼저** 실행되므로, 미등록 프로젝트에 대해서는 `deployments` 행 자체가 생성되지 않음

## 5. 데이터 흐름 (API별 테이블 접근)

| API | 테이블 접근 | 세부 동작 |
|---|---|---|
| GET /healthz | 없음 | 인증 미들웨어 이전에 응답, DB 미접근 |
| POST /deploy | projects(R), deployments(W) | `orchestrator.execute()`: `recordDeployment`(INSERT) → `getProject`(SELECT) → 성공 시 `setImages`(UPDATE projects) → `updateDeploymentStatus`(UPDATE deployments) |
| POST /projects | projects(W) | `upsertProject`: `INSERT ... ON CONFLICT(name) DO UPDATE` |
| DELETE /projects/:name | projects(W) | `removeProject`: `DELETE FROM projects` (deployments 미삭제) |
| GET /status | projects(R) | `listProjects`: `SELECT * FROM projects ORDER BY name` |
| GET /status/:project | projects(R), deployments(R) | `getProject` + `listDeployments`(project 일치, LIMIT 기본 20, id DESC) |
| GET /logs/:project | 없음 | `docker.logs`만 호출, DB 미접근 |
| POST /rollback/:project | projects(R/W), deployments(W) | `orchestrator.doRollback()`: `getProject`(SELECT) → `recordDeployment`(INSERT) → 성공 시 `setImages`(UPDATE projects) → `updateDeploymentStatus`(UPDATE deployments) |
| PUT /env/:project | 없음 | 파일시스템(`state/env/<project>.env`)만 조작, DB 미접근 |

## 6. 상태 전이 (deployments.status)

### 6.1 초기값

- INSERT 시점(`recordDeployment`)에 컬럼 `DEFAULT 'pending'` 자동 적용 — 호출부에서 status를 명시하지 않음(store.ts:65-70)

### 6.2 전이 경로 및 updateDeploymentStatus 호출 지점 (packages/deployer/src/orchestrator.ts)

| 전이 | 호출 지점 | 조건 |
|---|---|---|
| pending → success | orchestrator.ts:127 (`execute()`) | `swapContainer` 성공 |
| pending → failed | orchestrator.ts:119 (`execute()`) | `swapContainer` 실패 |
| pending → failed | orchestrator.ts:131 (`execute()` catch) | `execute()` try 블록 내 예외(예: `docker.pull` 실패, `getProject`가 undefined) |
| pending → rolled_back | orchestrator.ts:150 (`doRollback()`) | `swapContainer` 성공 |
| pending → failed | orchestrator.ts:146 (`doRollback()`) | `swapContainer` 실패 |
| pending → failed | orchestrator.ts:154 (`doRollback()` catch) | `doRollback()` try 블록 내 예외 |

### 6.3 예외 처리

- 모든 `updateDeploymentStatus` 호출은 `safeUpdateStatus`(orchestrator.ts:160-167)를 경유 — `id === undefined`면 no-op, `store.updateDeploymentStatus` 자체가 실패해도 catch로 무시(best-effort). 상태 기록 실패가 배포/롤백의 성공·실패 판정(HTTP 응답)에 영향을 주지 않음
- `doRollback()`에서 `getProject`가 undefined이거나 `previousImage`가 없는 경우(orchestrator.ts:139-141)는 `id`가 발급되지 않아 상태 전이 자체가 발생하지 않음(deployments 행 미생성)

## 7. 파일 시스템 상태 (env 파일)

| 항목 | 값 | 근거 |
|---|---|---|
| 저장 경로(컨테이너 내부) | `${envDir}/${project}.env` | app.ts PUT /env/:project, `envDir = join(stateDir, 'env')`(index.ts:16) |
| NAS 호스트 실제 경로 | `/volume1/docker/hoster/state/env/<프로젝트>.env` | STATE_DIR=/state ↔ `/volume1/docker/hoster/state`(docker-compose.yml volumes) |
| 파일 권한 | 0600 | `writeFileSync(file, ..., { mode: 0o600 })` + `chmodSync(file, 0o600)`(app.ts:170-177) — `mode` 옵션은 신규 생성 시에만 적용되므로 기존 파일 덮어쓸 때도 `chmodSync`로 0600 강제 |
| 형식 | 줄 단위 `KEY=VALUE`, 파일 끝 개행 | app.ts:170-174 |
| 관리 주체(단일 진입점) | `PUT /env/:project` (app.ts) | — |

### 7.1 PUT /env/:project 처리 절차

1. `mkdirSync(envDir, { recursive: true })`
2. 기존 파일 존재 시 줄 단위 파싱 → `Map<string,string>` (빈 줄/`#` 시작 줄 제외, `=` 첫 위치 기준 key/value 분리)
3. `body.set`(Record<string,string>) 적용 — 키는 `ENV_KEY_RE = /^[A-Za-z_][A-Za-z0-9_]*$/` 검증, 값은 개행 문자(`/[\r\n]/`) 포함 시 400
4. `body.remove`(string[]) 적용 — 존재 여부 확인 없이 무조건 삭제 시도
5. `[...current.entries()].map(([k,v]) => \`${k}=${v}\`).join('\n') + '\n'`로 전체 재작성

### 7.2 읽기 (orchestrator.ts readEnv)

- `swapContainer` 실행 시 `docker.run`의 `env: string[]` 인자로 사용(orchestrator.ts:44-51, 196-198)
- 파일 없으면 빈 배열 반환, 줄 단위 `trim()` 후 빈 줄/`#` 시작 줄 제외

## 8. 확인 안 되어 제외한 항목

- SQLite 파일 크기/VACUUM 정책 — 코드상 별도 처리 없음(확인된 사실 없어 기술 생략)
- 백업 정책 — 소스에 관련 코드 없음
- `better-sqlite3`의 `synchronous` PRAGMA 등 WAL 외 추가 PRAGMA 설정 — store.ts에 `journal_mode` 외 PRAGMA 없음

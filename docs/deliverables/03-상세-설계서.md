## 3. deployer 모듈별 상세

### 3.1 src/hmac.ts

```ts
function signPayload(body: string, timestampMs: number, secret: string): string
function verifySignature(opts: {
  body: string; timestampMs: number; signature: string; secret: string;
  nowMs?: number; maxSkewMs?: number;
}): boolean
```

- `signPayload`: `HMAC-SHA256(secret, "${timestampMs}.${body}")` → hex 문자열
- `verifySignature`:
  - `timestampMs`가 `Number.isFinite`가 아니면 false
  - `|nowMs - timestampMs| > maxSkewMs`(기본 300_000ms = 5분) 이면 false — 재전송(replay) 방지
  - `maxSkewMs` 기본값: `opts.maxSkewMs ?? 300_000`
  - `nowMs` 기본값: `opts.nowMs ?? Date.now()`
  - `signature`를 hex `Buffer`로 파싱 실패 시 false
  - `given.length !== expected.length` 이면 false (길이 다르면 `timingSafeEqual`이 예외를 던지므로 사전 체크)
  - `timingSafeEqual`로 상수 시간 비교

### 3.2 src/store.ts

```ts
class StateStore {
  constructor(dbPath: string)
  upsertProject(p: ProjectInput): void
  getProject(name: string): Project | undefined
  listProjects(): Project[]
  removeProject(name: string): void
  setImages(name: string, current: string | null, previous: string | null): void
  recordDeployment(d: { project: string; image: string; sha: string }): number
  updateDeploymentStatus(id: number, status: 'pending' | 'success' | 'failed' | 'rolled_back', error?: string): void
  listDeployments(project: string, limit = 20): Deployment[]
}
```

- 생성자: `new Database(dbPath)` → `pragma('journal_mode = WAL')` → `CREATE TABLE IF NOT EXISTS` (projects, deployments) 실행
- `upsertProject`: `INSERT ... ON CONFLICT(name) DO UPDATE` — `name`은 고정(PK), 나머지 컬럼만 갱신. `current_image`/`previous_image`는 건드리지 않음(별도 `setImages`로만 갱신)
- `getProject`/`listProjects`: SELECT 후 `rowToProject`로 snake_case → camelCase 매핑
- `removeProject`: `DELETE FROM projects WHERE name = ?` — deployments 행은 삭제되지 않고 그대로 남음(FK/CASCADE 없음)
- `setImages`: `current_image`/`previous_image` 동시 UPDATE
- `recordDeployment`: INSERT 후 `lastInsertRowid` 반환. `status`는 컬럼 DEFAULT `'pending'`이 적용됨(호출부에서 명시하지 않음)
- `updateDeploymentStatus`: `status`/`error` UPDATE (`error` 미지정 시 `null`)
- `listDeployments`: `project` 일치 + `LIMIT`(기본 20), `id DESC` 정렬

### 3.3 src/docker.ts

```ts
class DockerManager {
  constructor(opts?: { docker?: Dockerode; network?: string; ghcrPat?: string })
  pull(image: string): Promise<void>
  run(opts: { name: string; image: string; domain: string; containerPort: number; env: string[] }): Promise<void>
  stop(name: string): Promise<void>
  start(name: string): Promise<void>
  stopAndRemove(name: string): Promise<void>
  rename(from: string, to: string): Promise<void>
  logs(name: string, tail = 200): Promise<string>
  removeImage(image: string): Promise<void>
  healthCheck(url: string, timeoutMs = 60_000): Promise<boolean>
}
```

- `pull`: `ghcrPat` 있으면 `{ username: 'x', password: ghcrPat, serveraddress: 'ghcr.io' }` authconfig 구성, `followProgress`로 완료까지 대기
- `run`: `createContainer` + `start`. Labels:
  - `traefik.enable: 'true'`
  - `traefik.http.routers.${name}.rule: Host(\`${domain}\`)`
  - `traefik.http.services.${name}.loadbalancer.server.port: String(containerPort)`
  - `hoster.managed: 'true'`
  - `HostConfig.NetworkMode = this.network`, `RestartPolicy.Name = 'unless-stopped'`
- `stop`/`start`/`stopAndRemove`/`removeImage`: 실패 시 `ignoreAlreadyInTargetState`로 필터링 — statusCode 404/304만 무시, 그 외는 재던짐
- `rename`: dockerode `container.rename` 그대로 위임 (예외 무처리 — 호출부(orchestrator)가 try/catch로 감쌈)
- `healthCheck(url, timeoutMs=60_000)`: `deadline = Date.now() + timeoutMs`까지 1초 간격 폴링. `fetch(url, { redirect: 'manual', signal: AbortSignal.timeout(3000) })`, `res.status < 400`이면 true. fetch 예외는 무시하고 재시도. 데드라인 초과 시 false
- `logs`: dockerode `logs({ stdout: true, stderr: true, tail })` → `demux()`로 8바이트 프레임 헤더(0번째 바이트: 스트림 종류, 4~7번째 바이트: payload 길이, big-endian) 제거해 순수 텍스트만 추출. 불완전한 프레임(`end > buf.length`)은 안전하게 중단
- `ignoreAlreadyInTargetState(e)`: `statusCode !== 404 && statusCode !== 304`이면 재던짐. start의 304가 특히 중요 — 롤백 경로는 stop 실패 후에도 start를 호출하는데 이때 old 컨테이너는 대개 이미 실행 중이므로, 여기서 던지면 데몬 장애 같은 진짜 원인이 "already started"로 가려짐

### 3.4 src/orchestrator.ts

```ts
class Orchestrator {
  constructor(opts: { store: StateStore; docker: DockerManager; envDir: string })
  deploy(req: { project: string; image: string; sha: string }): Promise<{ status: 'success' | 'failed' | 'skipped'; error?: string }>
  rollback(project: string): Promise<{ status: 'success' | 'failed'; error?: string }>
  readEnv(project: string): string[]
}
```

**큐 상태**

- `running: Set<string>` — 프로젝트별 실행 중 여부(뮤텍스), deploy/rollback 공용
- `queues: Map<string, Job[]>` — 프로젝트별 대기 큐

**큐 규칙 (enqueue)**

1. 해당 프로젝트가 `running`에 없으면: `running`에 추가 후 즉시 `runJob` 실행
2. 실행 중이면 큐에 추가:
   - `kind === 'deploy'`: 큐에 대기 중이던 기존 deploy Job은 전부 `resolve({ status: 'skipped' })` 처리 후 제거(**latest-wins**) — 대기 중인 rollback Job은 건드리지 않음(순서 유지)
   - `kind === 'rollback'`: 그대로 큐 끝에 push — **skip되지 않고 FIFO로 대기** (deploy처럼 교체/스킵되는 대상이 아님)

**drain**

- 큐가 비었으면 `running`에서 제거(락 해제)
- 비어있지 않으면 큐 맨 앞(FIFO, `shift()`)의 job을 다음으로 실행

**runJob**

- `execute`/`doRollback` 호출 결과를 항상 `resolve` — 두 함수 모두 내부에서 항상 resolve하도록 설계돼 있으나, 예상치 못한 예외로 락이 영구히 걸리는 일이 없도록 한 번 더 try/catch로 감싸는 안전망
- 예외 발생 시 `job.resolve({ status: 'failed', error: e.message })`
- `finally`에서 항상 `drain(project)` 호출

**execute(req) — deploy**

1. `id = store.recordDeployment(req)` (상태 컬럼 기본값 `'pending'`)
2. `store.getProject(req.project)` — 없으면 `Error('unknown project')` (주의: recordDeployment가 이 검증보다 먼저 실행됨 → 미등록 프로젝트로 배포 요청 시에도 deployments 행이 먼저 생성된 뒤 실패 처리됨)
3. `docker.pull(req.image)`
4. `swapContainer(project, image)` 호출 — 실패 시 `safeUpdateStatus(id, 'failed', swap.error)` 후 `{ status: 'failed' }` 반환
5. 성공 시: `dropped = p.previousImage` 저장 → `store.setImages(project, image, p.currentImage)`(새 currentImage=배포 이미지, 새 previousImage=이전 currentImage) → `dropped`가 존재하고 새 image/새 previousImage와 다르면 `docker.removeImage(dropped)`
6. `safeUpdateStatus(id, 'success')` → `{ status: 'success' }`
7. try 블록 전체의 예외(catch): `safeUpdateStatus(id, 'failed', msg)` → `{ status: 'failed', error: msg }`

**doRollback(project) — rollback**

1. `store.getProject(project)` — 없으면 `{ status: 'failed', error: 'unknown project' }` (id 미발급, deployments 행 생성 안 됨)
2. `p.previousImage`가 없으면 `{ status: 'failed', error: 'no previous image' }` (id 미발급)
3. `target = p.previousImage`, `id = store.recordDeployment({ project, image: target, sha: 'rollback' })`
4. `swapContainer(project, target)` — 실패 시 `safeUpdateStatus(id, 'failed', ok.error)` 후 `{ status: 'failed' }`
5. 성공 시: `store.setImages(project, target, p.currentImage)`(새 currentImage=이전 currentImage였던 target, 새 previousImage=버려지는 기존 currentImage) → `safeUpdateStatus(id, 'rolled_back')` → `{ status: 'success' }`
6. try 블록 전체의 예외(catch): `safeUpdateStatus(id, 'failed', msg)`

**safeUpdateStatus**

- `id === undefined`이면 즉시 반환(no-op)
- `store.updateDeploymentStatus` 호출 실패는 무시(best-effort) — 상태 기록 실패가 배포/롤백 자체의 성공·실패 판정에 영향을 주지 않도록 함

**swapContainer(project, image) — 절차**

기존 컨테이너를 `-old`로 rename하고 새 이미지를 기동, 헬스체크 후 확정. 실패 시 원복.

1. `hoster-${project}-old` 잔존 컨테이너를 `stopAndRemove`로 우선 정리 (직전 롤백 실패 잔재 등 대비)
2. 기존 `hoster-${project}` 컨테이너를 `-old`로 `rename` 시도 — 성공하면 `renamed = true`, 실패(최초 배포로 컨테이너 없음)하면 `renamed = false`
3. (`renamed === true`인 경우) `-old` 컨테이너를 `stop`(제거 아님) — rename은 Docker 라벨을 바꾸지 않으므로 `-old` 컨테이너는 여전히 새 컨테이너와 동일한 Traefik 라우터/서비스 라벨을 가짐. 실행 중인 채로 두면 헬스체크가 끝날 때까지(최대 60초) Traefik이 같은 라우터에 old+new 두 백엔드를 동시에 등록해 미검증 신규 컨테이너로도 트래픽이 흐를 수 있음. Traefik의 docker 프로바이더는 실행 중인 컨테이너만 반영하므로 즉시 정지시켜 라우팅에서 제외. 롤백 시 다시 살릴 수 있어야 하므로 `stopAndRemove`가 아닌 `stop`
4. `docker.run({ name, image, domain, containerPort, env: readEnv(project) })`로 신규 이름/이미지 컨테이너 기동
5. `docker.healthCheck("http://${name}:${containerPort}${healthPath}")` 수행 — 실패 시 `Error('health check failed')` throw
6. 성공: `renamed === true`이면 `-old` 컨테이너 `stopAndRemove`(완전 제거) → `{ success: true }`
7. 실패(catch): 신규 컨테이너 `stopAndRemove`로 정리 → `renamed === true`이면 `rename(oldName, name)`으로 원래 이름 복구 후 반드시 `start(name)` 호출(위에서 `stop`시켜 뒀으므로 rename만으로는 서비스가 복구되지 않음) → `{ success: false, error: e.message }`
8. 위 3번 단계의 `stop(oldName)` 호출은 반드시 catch로 보호되는 try 블록 안에 있어야 함 — 밖에 있으면 데몬 일시 장애로 404/304가 아닌 에러를 던졌을 때 원복 로직이 전혀 실행되지 못하고 서비스가 `-old` 상태로 완전히 멈춘 채 남음

**readEnv(project)**

- `${envDir}/${project}.env` 파일 읽기, 없으면 빈 배열 반환
- 줄 단위 `trim()` 후 빈 줄과 `#`으로 시작하는 줄 제외

### 3.5 src/app.ts

```ts
function buildApp(deps: {
  store: StateStore; docker: DockerManager; orchestrator: Orchestrator;
  secret: string; envDir: string; baseDomain: string;
}): Hono<AppEnv>
```

**검증 정규식**

```ts
const PROJECT_NAME_RE = /^[a-z0-9][a-z0-9-]{0,62}$/;
const HOSTNAME_RE = /^(?=.{1,253}$)([a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?)(\.[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?)+$/i;
const ENV_KEY_RE = /^[A-Za-z_][A-Za-z0-9_]*$/;
```

- `PROJECT_NAME_RE`: 프로젝트명은 컨테이너명·env 파일 경로·기본 도메인 라벨에 그대로 쓰이므로 DNS 라벨 형태로만 허용
- `HOSTNAME_RE`: `POST /projects`의 `domain`은 Traefik 라우터 라벨(백틱 규칙)에 그대로 삽입되므로 호스트명 형식만 허용
- `ENV_KEY_RE`: `.env` 파일에 그대로 쓰이는 키는 통상적인 식별자 형태만 허용

**미들웨어/공통**

- `GET /healthz`: 인증 미들웨어(`app.use('*', ...)`) 등록보다 먼저 등록되어 서명 없이 응답 — 라우트 등록 순서에 의존하는 의도된 예외(터널/모니터링용)
- 인증 미들웨어: `c.req.path === '/healthz'`면 통과. `GET`/`DELETE`는 `body = ''`(서명 대상에서 제외), 그 외 메서드는 `await c.req.text()`로 읽은 본문을 서명 대상에 포함. `verifySignature` 실패 시 401. 통과 시 `rawBody`를 컨텍스트 변수(`c.set('rawBody', body)`)로 저장
- `getBody<T>(c)`: `c.get('rawBody')`를 `JSON.parse`, 실패 시 400 `Response`를 그대로 반환해 각 라우트의 중복 처리 제거

**라우트**

| 메서드/경로 | 검증 | 동작 | 응답 |
|---|---|---|---|
| GET /healthz | 없음 | — | `{ ok: true }` |
| POST /deploy | project(PROJECT_NAME_RE), image/sha(string) | `orchestrator.deploy({project, image, sha})` | `result`, status==='failed'면 500 아니면 200 |
| POST /projects | name(PROJECT_NAME_RE), imageRepo(non-empty string), domain(HOSTNAME_RE, 미지정 시 `${name}.${baseDomain}` 기본값) | `store.upsertProject` (branch 기본 'main', containerPort 기본 3000, healthPath 기본 '/') | `{ ok: true }` |
| DELETE /projects/:name | name(PROJECT_NAME_RE) | `docker.stopAndRemove('hoster-'+name')` → `store.removeProject(name)` | `{ ok: true }` |
| GET /status | 없음 | `store.listProjects()` | 프로젝트 배열 |
| GET /status/:project | project(PROJECT_NAME_RE) | `store.getProject` + `store.listDeployments` | 프로젝트+`deployments`, 없으면 404 |
| GET /logs/:project | project(PROJECT_NAME_RE) | `tail` 쿼리(정수 아니면 기본 200), `docker.logs('hoster-'+project, tail)` | text |
| POST /rollback/:project | project(PROJECT_NAME_RE) | `orchestrator.rollback(project)` | `result`, status==='failed'면 500 아니면 200 |
| PUT /env/:project | project(PROJECT_NAME_RE), set 키(ENV_KEY_RE)/값(개행 금지: `/[\r\n]/` 불가), remove(string[]) | 기존 파일 파싱(Map) → set 적용 → remove 적용 → 재작성 | `{ ok: true, keys: [...] }` |

**PUT /env/:project 상세**

1. `mkdirSync(envDir, { recursive: true })`
2. `${envDir}/${project}.env` 존재 시 줄 단위 파싱(`#`/빈 줄 제외, `=` 첫 위치 기준 key/value 분리) → `Map<string,string>`
3. `setEntries` 적용(덮어쓰기) → `removeList` 적용(삭제)
4. `writeFileSync(file, "KEY=VALUE\n"..., { mode: 0o600 })`
5. `chmodSync(file, 0o600)` — `writeFileSync`의 `mode` 옵션은 파일이 새로 생성될 때만 적용되므로, 기존 파일(예: 이전 버전이 0644로 남긴 파일)을 덮어쓸 때도 0600을 강제하기 위한 추가 호출

- `deleteDnsRecord`: `type=CNAME`으로 좁혀 검색 후 DELETE — 타입 필터 없이 이름만으로 찾으면 같은 이름의 다른 타입 레코드(예: TXT)를 대신 지우고 정작 지워야 할 CNAME은 남길 위험이 있어 반드시 타입 지정


**정규식 원문**

```ts
const GITHUB_SEGMENT_RE = /^[A-Za-z0-9._-]+$/;
const PROJECT_NAME_RE = /^[a-z0-9][a-z0-9-]{0,62}$/;
const SAFE_BRANCH_RE = /^[A-Za-z0-9][A-Za-z0-9._/-]{0,199}$/;
```

- `parseGitHubRepo`: `remoteUrl.trim().match(/github\.com[:/]([^/]+)\/([^/]+?)(\.git)?$/)`로 owner/repo 추출, 매치 실패 시 `Error("GitHub 원격이 아닙니다: ...")`. 각 세그먼트를 `GITHUB_SEGMENT_RE`로 검증 — GitHub의 실제 owner/repo 문자 집합(영숫자, 마침표, 밑줄, 하이픈)만 허용. 기존 `[^/]+` 패턴은 슬래시만 아니면 따옴표/개행까지 통과시켜, origin 리모트를 조작할 수 있는 공격자가 `templates/workflow.yml.tpl`(YAML 문자열+셸 이중따옴표 문자열)에 YAML/셸을 주입할 수 있었음
- `PROJECT_NAME_RE`: `packages/deployer/src/app.ts`의 동명 정규식과 반드시 일치해야 함(문자열 원문 동일)
- `isValidBranchName`: `SAFE_BRANCH_RE` 통과 + `..` 미포함 + `//` 미포함 + `/`로 끝나지 않음 + `.lock`로 끝나지 않음. git-check-ref-format 전체 규칙 대신, 이 브랜치명이 삽입되는 두 컨텍스트(workflow.yml.tpl의 YAML 큰따옴표 문자열, printf 안의 셸 이중따옴표 문자열) 모두에서 안전한 보수적 부분집합만 허용(따옴표/개행/셸 메타문자/백슬래시 전부 배제)
- `projectNameOf(repo)`: 소문자화 → `[^a-z0-9-]+`를 `-`로 치환 → 연속 하이픈 축약(`-+` → `-`) → 양끝 하이픈 제거 → 63자 초과 시 `slice(0, 63)` 후 끝 하이픈 재제거 → 빈 문자열이면 `Error('저장소 이름("${repo}")에서 유효한 프로젝트명을 만들 수 없습니다. --project 옵션으로 직접 지정하세요.')`
- `imageRepoOf(owner, repo)`: `` `ghcr.io/${owner}/${repo}`.toLowerCase() `` — GHCR는 저장소 경로가 전부 소문자여야 하나 GitHub 저장소명 자체는 대소문자 허용(`parseGitHubRepo`는 원본 대소문자 보존)하므로 이미지 경로 구성 시점에 별도 소문자화
- `renderTemplate`: `tpl.replace(/\{\{(\w+)\}\}/g, ...)`로 치환, 치환 후 남은 `{{...}}` 토큰이 있으면 `Error("템플릿 토큰 미지정: ...")`
- `detectNextJs`: `pkg.dependencies?.next ?? pkg.devDependencies?.next`의 진위값

### 4.10 src/commands/init.ts

```ts
function planInit(input: { baseDomain: string; nas: { host: string; port: number; user: string } }): InitAction[]
function runInit(opts: { dryRun: boolean; stackDir: string; reuseTunnelId?: string; deps?: InitDeps }): Promise<void>
```

**planInit — 12단계 (순서 고정)**

1. `local-exec`(id: `ssh-docker-precheck`) — NAS 접속 및 docker 권한 사전 점검: `ssh -p ${port} ${user}@${host} 'sudo -n /usr/local/bin/docker version --format {{.Server.Version}}'`
2. `nas-exec`(id: `compose-check`) — docker compose 플러그인 확인: `sudo -n /usr/local/bin/docker compose version`
3. `cf-api`(method: `createTunnel`, args: `['hoster']`) — Cloudflare 터널 'hoster' 생성
4. `cf-api`(method: `setTunnelIngress`) — 터널 인그레스 설정: `hoster.<baseDomain>` → `http://hoster-deployer:8080`, `*.<baseDomain>` → `http://hoster-traefik:80`
5. `cf-api`(method: `upsertDnsCname`) — DNS CNAME 설정: `hoster.<baseDomain>` → `${TUNNEL_ID}.cfargotunnel.com`
6. `nas-exec`(id: `network-create`) — `hoster-net` 네트워크 생성(이미 있으면 무시): `sudo -n /usr/local/bin/docker network create hoster-net`
7. `nas-transfer` — NAS 상태 디렉터리 준비(`mkdir -p /volume1/docker/hoster/state/env`) 및 stack 디렉터리 전송(docker-compose.yml)
8. `local-exec` — deployer 이미지 빌드(linux/amd64) 후 NAS로 전송: `docker buildx build ... --load . && docker save ... | gzip | ssh ... 'gunzip | sudo -n /usr/local/bin/docker load'`
9. `nas-exec`(id: `env-write`) — `.env` 파일 작성(mode 0600) 및 `docker compose up -d`: `printf 'TUNNEL_TOKEN=%s\nHMAC_SECRET=%s\nGHCR_PAT=%s\nBASE_DOMAIN=%s\n' ... > /volume1/docker/hoster/.env && chmod 600 ...`
10. `write-config` — `~/.hoster/config.json` 저장 — **healthz 확인(11~12단계)보다 반드시 먼저 실행**: 이 시점 이후 실패(네트워크 진단 경고, healthz 재시도 6회 소진)는 로컬 설정 저장을 막을 이유가 아님. 터널/DNS/`.env`(HMAC_SECRET 포함)는 이미 NAS에 존재하므로, 여기서 저장하지 않으면 재시도 시 시크릿/터널ID를 알 방법이 없어 터널 이름 충돌에 부딪힘
11. `nas-exec`(id: `network-diagnostic`) — `hoster-net` 외부 통신 진단: `sudo -n /usr/local/bin/docker run --rm --network hoster-net alpine:3.20 wget -q -O- -T 10 https://one.one.one.one`
12. `local-exec`(id: `healthz-check`) — 터널 경유 healthz 확인(전파 지연 대비 10초 간격 6회 재시도): `curl -fsS https://hoster.<baseDomain>/healthz`

- `planInit`은 순수 함수(I/O 없음) — 시크릿(TUNNEL_TOKEN/HMAC_SECRET/GHCR_PAT)이 `InitInput`에 존재하지 않으므로 결과물에 실제 시크릿 값이 섞이지 않음. 커맨드 문자열에는 `${...}` 플레이스홀더만 남고, 실제 치환은 `runInit`이 실행 시점에 수행

**runInit — 실행 흐름**

1. `--dry-run`이면 계획(`planInit` 결과)만 로그로 출력하고 종료
2. Cloudflare API 토큰(`askHidden`) → Account ID(`ask`) → Zone ID(`ask`) → GHCR PAT(`askHidden`) 순서로 프롬프트
3. `HMAC_SECRET`은 `randomBytes(32).toString('hex')`로 자동 생성(사용자 입력 없음)
4. plan을 순회하며 `kind`별 분기:
   - `local-exec`: `substitutePlaceholders`로 `BASE_DOMAIN`만 치환. `id === 'healthz-check'`면 `retry(fn, 6, 10_000, sleep)`(실패 시 `Error("healthz 확인 실패 (6회 재시도): ...")`), 그 외는 1회 실행 후 `code !== 0`이면 `Error("로컬 명령 실패: ...")`
   - `nas-exec`: `TUNNEL_TOKEN`/`HMAC_SECRET`/`GHCR_PAT`/`BASE_DOMAIN` 치환 후 `nas.exec(cmd)`. 실패 시 id별 관용 처리: `network-create` + 메시지에 `exists` 포함 → 로그만 남기고 무시, `network-diagnostic` → throw하지 않고 `warn()`만(cloudflared가 hoster-net 위에서 실행되며 외부 통신이 필수이므로 무시 가능하다고 안내하지 않음), 그 외 → 그대로 throw
   - `nas-transfer`: `nas.exec(STATE_DIR_CMD)` → `nas.transferDir(stackDir, REMOTE_TMP_DIR)` → `cp -a ${REMOTE_TMP_DIR}/${base}/. ${REMOTE_STACK_DIR}/ && rm -rf ${REMOTE_TMP_DIR}`
   - `cf-api`: `method === 'createTunnel'`이면 `reuseTunnelId` 있을 시 `getTunnelToken`만 호출, 없으면 `createTunnel` 호출(이름 충돌 시 `TUNNEL_NAME_CONFLICT_RE = /already exists|duplicate/i` 매치되면 안내 메시지로 치환해 throw). 그 외 메서드는 `substituteArgs`로 `${TUNNEL_ID}`를 실제 값으로 치환 후 호출
   - `write-config`: `HosterConfig` 구성 후 `saveConfig(cfg)`
5. 실패 시 `printRecoveryNote(log, progress)`로 진행 상태(`stackTransferred`/`envWritten`/`configSaved`) 기반 복구 안내 후 재throw — 시크릿 값 자체는 절대 포함하지 않음

### 4.11 src/commands/add.ts

```ts
function runAdd(opts: { branch: string; project?: string; cwd: string; dryRun: boolean; force?: boolean; deps?: AddDeps }): Promise<void>
```

1. `git remote get-url origin` 조회 실패 시 `Error("git 원격(origin) 조회 실패: ...")`
2. `parseGitHubRepo(remote.stdout)` → `owner`, `repo`
3. `projectName = opts.project ?? projectNameOf(repo)`, `imageRepo = imageRepoOf(owner, repo)`
4. **파일 쓰기 전** `isValidBranchName(opts.branch)`/`isValidProjectName(projectName)` 검증 — `branch`/`project`는 `templates/workflow.yml.tpl`에 YAML 문자열과 셸 이중따옴표 문자열(printf 안) 양쪽으로 그대로 삽입되므로 반드시 선검증. `--project`는 `projectNameOf()`를 거치지 않는 유일한 경로라 특히 중요
5. `--dry-run`: 6단계 계획 로그만 출력(파일/시크릿/DNS/등록 아무것도 실행하지 않음)
6. `ensureGhReady(run, cwd)` — `gh --version` 실패 시 설치 안내, `gh auth status` 실패 시 로그인 안내. **가장 먼저 수행** — 이후 단계(Dockerfile/workflow 생성 등)가 이미 실행된 뒤 gh 없음으로 중단되면 저장소가 "반쯤 설정된" 상태로 남기 때문
7. `loadConfig()`
8. Dockerfile 없고 Next.js 감지(`detectNextJs`) 시 `Dockerfile.nextjs.tpl` 생성, `next.config`에 `standalone` 미포함 시 경고. Dockerfile 없고 Next.js도 아니면 직접 추가 안내만
9. workflow 파일(`.github/workflows/hoster-deploy.yml`) 없거나 `--force`면 `renderTemplate(workflow.yml.tpl, {BRANCH, PROJECT, IMAGE_REPO})`로 생성. 있고 `--force` 없으면 보존(건드리지 않음)
10. `gh secret set HOSTER_DEPLOY_URL --repo ${owner}/${repo}` (stdin으로 `config.deployerUrl` 전달), `gh secret set HOSTER_DEPLOY_SECRET`(stdin으로 `config.hmacSecret` 전달) — argv 대신 stdin 사용은 `ps` 등으로 다른 사용자에게 노출되는 것을 막기 위함
11. `cf.upsertDnsCname(dnsName, "${tunnelId}.cfargotunnel.com")` → `client.registerProject({ name, imageRepo, branch })`
12. DNS 생성과 프로젝트 등록 사이 원자성 없음 — `dnsCreated` 플래그로 실패 시 어디까지 완료됐는지 구분해 안내(재시도 시 DNS는 upsert이므로 안전)

### 4.12 src/commands/ops.ts

```ts
function parseEnvArgs(args: string[]): Record<string, string>
function formatLs(projects: { name: string; domain: string; currentImage: string | null }[]): string
function runLs(deps: LsDeps): Promise<void>
function runStatus(project: string, deps: StatusDeps): Promise<void>
function runLogs(project: string, tail: number, deps: LogsDeps): Promise<void>
function runRollback(project: string, deps: RollbackDeps): Promise<void>
function inferProjectName(run: Runner, cwd: string): Promise<string>
function runEnv(action: 'set' | 'rm', args: string[], opts: EnvOpts, deps: EnvDeps): Promise<void>
function runRemove(project: string, deps: RemoveDeps): Promise<void>
function runDoctor(deps: DoctorDeps): Promise<void>
```

- `runLs`: `client.status()` → 빈 배열이면 "등록된 프로젝트가 없습니다." 안내, 아니면 `formatLs`로 정렬된 표 출력(NAME/DOMAIN/IMAGE, IMAGE는 태그 앞 7자)
- `runStatus`: `client.statusOf(project)` → 이름/도메인/현재·이전 이미지/최근 배포 이력(`#id  createdAt  status  shortImage  error=...`) 출력
- `runLogs`: `client.logs(project, tail)` 그대로 출력
- `friendlyDeployerErrorMessage(e)`: `DeployerClient.request`가 2xx 아닌 응답에서 던지는 `` `deployer 응답 ${status}: ${rawBody}` `` 형태 메시지에서 `rawBody`가 JSON이고 `error` 필드가 문자열이면 그 값만 추출해 반환, 아니면 원본 메시지 그대로. deployer는 실패한 rollback/deploy에 HTTP 500을 반환하므로 성공적으로 반환되는 결과의 `status`는 실제로는 항상 `'success'`뿐이고 `'failed'`는 절대 여기까지 오지 않음(항상 throw로 먼저 걸러짐) — 예전 `result.status !== 'success'` 분기는 도달 불가능한 죽은 코드였음
- `runRollback`: `client.rollback(project)` 실패 시 `Error("롤백 실패: " + friendlyDeployerErrorMessage(e))`
- `inferProjectName`: `git remote get-url origin` → `parseGitHubRepo` → `projectNameOf` — `hoster add`가 등록한 프로젝트명과 동일 규칙으로 추론해야 `hoster env`가 다른 이름을 만들어 "프로젝트 없음"을 유발하지 않음
- `runEnv`: `project = opts.project ?? inferProjectName(...)` → `client.env(project, {set: parseEnvArgs(args)} 또는 {remove: args})` → `--redeploy`면 `statusOf(project)`로 `currentImage` 확인(없으면 `Error`) → `sha = currentImage.split(':').pop()` → `client.deploy({project, image: currentImage, sha})` 재호출(실패 시 `friendlyDeployerErrorMessage`로 감싼 `Error("재배포 실패: ...")`)
- `runRemove`: `statusOf(project)`로 실제 `domain`을 **먼저** 조회 — `POST /projects`가 `domain`을 관례(`${project}.${baseDomain}`)와 다르게 저장할 수 있어(app.ts에서 명시적 domain을 받아 override 가능) 관례로 재구성하지 않음. `removeProject(project)`(성공 시 `deployerRemoved=true`) → `cf.deleteDnsRecord(domain)` — 두 원격 작업 사이 원자성 없어 실패 시 어디까지 완료됐는지 안내. workflow 파일은 자동 삭제되지 않음(안내만)
- `runDoctor`: `planInit(input)`에서 `id`로 `ssh-docker-precheck`/`compose-check`/`network-diagnostic` 액션만 찾아 재실행. **상태를 바꾸는 액션(터널/DNS 생성, 네트워크 생성, 이미지 빌드/전송, `.env` 작성/compose up)은 절대 실행하지 않음**. `network-diagnostic` 실패는 throw하지 않고 `warn()`만(외부 API 미사용 앱이면 무시 가능하다고 안내)

## 5. 에러 처리 설계

### 5.1 "항상 resolve" 계약 (Orchestrator)

- `Orchestrator.deploy()`/`rollback()`이 반환하는 `Promise`는 절대 reject하지 않음
- `runJob`이 `execute`/`doRollback` 결과를 무조건 `resolve`, 예외 발생 시에도 catch에서 `{ status: 'failed', error: e.message }` resolve
- 근거: reject를 허용하면 `running` Set의 락이 영구히 걸려, 해당 프로젝트의 이후 모든 deploy/rollback 요청이 큐에 쌓인 채 영원히 대기하게 됨(`finally { this.drain(project) }`가 실행되긴 하지만, 예외가 처리되지 않은 채 전파되면 상위 호출자가 `.catch` 없이 방치할 위험을 사전에 차단)

### 5.2 friendlyDeployerErrorMessage (packages/cli/src/commands/ops.ts)

- `DeployerClient.request`가 던지는 `` `deployer 응답 ${status}: ${rawBody}` `` 형태 메시지에서 `rawBody`의 JSON `error` 필드만 추출해 사용자에게 표시
- `runRollback`, `runEnv`(`--redeploy` 경로)에서 사용

### 5.3 부분 실패(원자성 없는 다단계 원격 작업) 안내

| 위치 | 실패 지점 | 안내 내용 |
|---|---|---|
| `commands/add.ts` `runAdd` | DNS 생성 성공 후 `registerProject` 실패 | DNS는 이미 생성됨(재시도 시 upsert로 안전), Dockerfile/workflow/gh secret은 이미 완료 |
| `commands/add.ts` `runAdd` | DNS 생성 자체 실패 | 프로젝트 등록은 시도하지 않음, Dockerfile/workflow/gh secret만 완료 |
| `commands/ops.ts` `runRemove` | `removeProject` 성공 후 `deleteDnsRecord` 실패 | deployer 등록/컨테이너는 제거됨, DNS는 Cloudflare 대시보드에서 직접 삭제 안내 |
| `commands/init.ts` `runInit` (`printRecoveryNote`) | 시크릿 생성 이후 임의 단계 실패 | `stackTransferred`/`envWritten`/`configSaved` 진행 상태만 정확히 안내(시크릿 값 자체는 절대 포함하지 않음). `envWritten`이면 재시도 시 HMAC_SECRET이 새로 생성됨을 경고 |

## 6. 주요 시퀀스 (개조식)

### 6.1 배포 성공 시퀀스 (POST /deploy)

1. 클라이언트(hoster CLI 또는 GitHub Actions workflow)가 `POST /deploy {project, image, sha}` 요청, HMAC 서명 헤더(`x-hoster-timestamp`, `x-hoster-signature`) 포함
2. app.ts 인증 미들웨어: `verifySignature` 통과
3. app.ts: `project`(PROJECT_NAME_RE)/`image`/`sha`(string) 검증
4. `orchestrator.deploy(req)` → `enqueue` → 해당 프로젝트가 idle이면 즉시 `runJob` → `execute(req)`
5. `store.recordDeployment(req)` — `id` 발급, status 기본값 `pending`
6. `store.getProject(project)` 확인
7. `docker.pull(image)`
8. `swapContainer` 실행:
   - `hoster-${project}-old` 잔존 정리
   - `hoster-${project}` → `hoster-${project}-old` rename
   - `-old` `stop`(Traefik 라우팅에서 제외)
   - `docker.run`으로 신규 이미지 기동(이름 `hoster-${project}`)
   - `healthCheck` 성공
   - `-old` `stopAndRemove`(완전 제거)
9. `store.setImages(project, image, 기존 currentImage)` — 새 currentImage=배포 이미지, 새 previousImage=기존 currentImage
10. 버려지는 이전 previousImage가 새 image/새 previousImage와 다르면 `docker.removeImage`로 정리
11. `store.updateDeploymentStatus(id, 'success')`
12. `drain(project)` — 대기 큐 있으면 다음 job 실행, 없으면 락 해제
13. `HTTP 200 { status: 'success' }`

### 6.2 헬스체크 실패 → 자동 롤백 시퀀스 (swapContainer 내부 원복)

1. 6.1과 동일하게 진행, `docker.run`까지 완료
2. `healthCheck`가 `timeoutMs`(기본 60초) 내 200번대 미만 응답을 받지 못해 `false` 반환
3. `Error('health check failed')` throw
4. catch 블록: 신규 `hoster-${project}` `stopAndRemove`
5. `renamed === true`였다면: `hoster-${project}-old` → `hoster-${project}` rename 복구 → `start()`로 재기동(3단계에서 `stop`시켜 뒀으므로 rename만으로는 부족)
6. `swapContainer`가 `{ success: false, error: 'health check failed' }` 반환
7. `execute()`: `store.updateDeploymentStatus(id, 'failed', 'health check failed')`
8. `HTTP 500 { status: 'failed', error: 'health check failed' }`
9. 이 경로에서 `store.setImages`는 호출되지 않음 — `currentImage`/`previousImage`는 배포 전 값 그대로 유지되며, 컨테이너는 원래 이미지로 계속 실행 중인 상태로 원복됨

### 6.3 rollback 명령 시퀀스 (hoster rollback → POST /rollback/:project)

1. CLI `runRollback` → `DeployerClient.rollback(project)` → `POST /rollback/:project`(HMAC 서명 포함)
2. app.ts 인증 통과 → `orchestrator.rollback(project)` → `enqueue({ kind: 'rollback' })`
3. 해당 프로젝트가 이미 실행 중(다른 deploy/rollback 처리 중)이어도 **skip되지 않고 큐 끝에 추가되어 FIFO로 대기** — 대기 중이던 deploy job이 있어도 그대로 유지(건드리지 않음), 새 rollback만 뒤에 push
4. 락 획득 시 `doRollback(project)` 실행
5. `store.getProject(project)` — 없으면 `{ status: 'failed', error: 'unknown project' }`
6. `p.previousImage` 없으면 `{ status: 'failed', error: 'no previous image' }`
7. `store.recordDeployment({ project, image: previousImage, sha: 'rollback' })`
8. `swapContainer(project, previousImage)` — 6.1의 8번과 동일 절차
9. 성공: `store.setImages(project, previousImage, 기존 currentImage)`(새 currentImage=previousImage였던 값, 새 previousImage=버려지는 기존 currentImage) → `store.updateDeploymentStatus(id, 'rolled_back')`
10. 실패: `store.updateDeploymentStatus(id, 'failed', error)`
11. CLI: 실패 시 `friendlyDeployerErrorMessage`로 에러 문구 정제 후 `Error("롤백 실패: ...")` throw. 성공 시 `프로젝트 "${project}"를 이전 이미지로 롤백했습니다.` 로그 출력

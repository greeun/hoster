## CLI 커맨드 명세 (9종)

### 1. `hoster init`

- 형식: `hoster init [options]`
- 플래그

| 플래그 | 기본값 | 설명 |
|---|---|---|
| `--dry-run` | (없음, boolean false) | 실행하지 않고 계획만 표시 |
| `--stack-dir <dir>` | `"stack/"` | stack 디렉터리 경로 |
| `--reuse-tunnel <id>` | (없음) | 기존 Cloudflare 터널 ID 재사용 |

- 동작 요약
  - `planInit()`이 생성한 순서대로 실행: NAS SSH/docker 권한 사전점검 → `docker compose version` 확인 → Cloudflare 터널 생성(`hoster`) → 터널 인그레스 설정(`hoster.<domain>`, `*.<domain>`) → DNS CNAME 설정 → `hoster-net` 네트워크 생성 → stack 디렉터리 전송 → deployer 이미지 빌드(`linux/amd64`) 후 NAS로 전송 → NAS `.env` 작성(mode 0600, `TUNNEL_TOKEN`/`HMAC_SECRET`/`GHCR_PAT`/`BASE_DOMAIN`) + `docker compose up -d` → `~/.hoster/config.json` 저장 → `hoster-net` 외부 통신 진단 → 터널 경유 `healthz` 확인
  - `HMAC_SECRET`은 CLI가 32바이트 랜덤 hex로 자동 생성
- 종료 조건
  - `--dry-run`: 계획 출력 후 정상 종료(작업 미실행)
  - `ssh-docker-precheck`/`compose-check`/터널 생성/DNS/네트워크 생성(이미 존재 시 무시)/스택 전송/이미지 빌드·전송/`.env` 작성 중 하나라도 실패 → 예외 발생, 진행 상태 안내(`printRecoveryNote`) 후 `exitCode=1`
  - 터널 이름 충돌(Cloudflare 응답에 `already exists`/`duplicate` 포함) → 안내 메시지로 재작성 후 실패 처리
  - `network-diagnostic` 실패 → 경고만 출력, 계속 진행(실패로 간주하지 않음)
  - `healthz-check` 실패 → 10초 간격 6회 재시도 후에도 실패 시 예외

### 2. `hoster add`

- 형식: `hoster add [options]`
- 플래그

| 플래그 | 기본값 | 설명 |
|---|---|---|
| `--branch <branch>` | `"main"` | 배포 대상 브랜치 |
| `--project <name>` | (없음, 레포 이름에서 추론) | 프로젝트명 |
| `--dry-run` | (없음, boolean false) | 실행하지 않고 계획만 표시 |
| `--force` | (없음, boolean false) | 기존 workflow 파일을 덮어씀 |

- 동작 요약
  - `git remote get-url origin`으로 owner/repo 파싱 → `--project` 미지정 시 `projectNameOf(repo)`로 프로젝트명 추론 → `imageRepoOf(owner, repo)`로 이미지 저장소 결정
  - Dockerfile 없고 Next.js 감지 시(`package.json`의 `dependencies.next`/`devDependencies.next`) `templates/Dockerfile.nextjs.tpl`로 생성
  - `.github/workflows/hoster-deploy.yml` 없거나 `--force` 지정 시 `templates/workflow.yml.tpl` 렌더링 후 생성
  - `gh secret set HOSTER_DEPLOY_URL`, `gh secret set HOSTER_DEPLOY_SECRET` (값은 stdin으로 전달)
  - Cloudflare DNS CNAME upsert(`<project>.<baseDomain>` → `<tunnelId>.cfargotunnel.com`) 후 deployer에 `registerProject` 호출
- 종료 조건
  - `--dry-run`: 계획 출력 후 정상 종료
  - git origin이 GitHub 형식 아님/owner·repo에 허용되지 않는 문자 포함 → 예외(`parseGitHubRepo`)
  - `branch`가 `SAFE_BRANCH_RE` 불일치, `..`/`//` 포함, `/`로 끝남, `.lock`으로 끝남 → 예외
  - 프로젝트명이 `PROJECT_NAME_RE`(`/^[a-z0-9][a-z0-9-]{0,62}$/`) 불일치 → 예외
  - `gh --version` 또는 `gh auth status` 실패(GitHub CLI 미설치/미로그인) → 예외
  - `gh secret set` 실패 → 예외
  - DNS upsert 또는 `registerProject` 실패 → 예외(어디까지 완료됐는지 안내 로그 후 rethrow)
  - 정상 완료 시 커밋/push 안내 로그 출력 후 종료

### 7. `hoster env`

- 형식
  - `hoster env set [options] <pairs...>`
  - `hoster env rm [options] <keys...>`
- 인자
  - `set`: `pairs...` — `KEY=VALUE` 목록(1개 이상)
  - `rm`: `keys...` — 제거할 키 목록(1개 이상)
- 플래그

| 플래그 | 적용 커맨드 | 기본값 | 설명 |
|---|---|---|---|
| `--project <name>` | set, rm 공통 | (없음, 현재 레포에서 추론) | 프로젝트명 |
| `--redeploy` | set 전용 | (없음, boolean false) | 변경 후 현재 이미지로 재배포 |

- 동작 요약
  - `set`: `KEY=VALUE` 파싱(`parseEnvArgs`, `=` 없으면 예외) 후 `PUT /env/:project` 호출(`{ "set": {...} }`)
  - `rm`: `PUT /env/:project` 호출(`{ "remove": [...] }`)
  - `--project` 미지정 시 `git remote get-url origin` → `parseGitHubRepo` → `projectNameOf(repo)` 순으로 추론(`hoster add`와 동일 규칙)
  - `--redeploy` 지정 시 `GET /status/:project`로 `currentImage` 조회 후 동일 이미지·SHA로 `POST /deploy` 재요청
- 종료 조건
  - `pairs`/`keys` 항목이 `KEY=VALUE` 형식 아님(`set`만 해당, `=` 위치가 0 이하) → 예외(`KEY=VAL 형식이어야 합니다: <값>`)
  - `--project` 미지정 + git origin 조회 실패 → 예외
  - `--redeploy` 시 `currentImage`가 없음 → 예외(`프로젝트 "<project>"에 배포된 이미지가 없어 재배포할 수 없습니다.`)
  - 재배포 API 실패 → `재배포 실패: <message>`로 예외

### 8. `hoster remove`

- 형식: `hoster remove <project>`
- 인자: `project` (필수)
- 플래그: 없음
- 동작 요약
  - `GET /status/:project`로 실제 `domain` 조회 (관례로 `${project}.${baseDomain}`을 재구성하지 않음 — `POST /projects`가 임의 domain을 허용하므로)
  - `DELETE /projects/:project` 호출 후 Cloudflare DNS 레코드 삭제(`deleteDnsRecord`)
  - workflow 파일(`.github/workflows/hoster-deploy.yml`)은 자동 삭제되지 않음(안내 로그만 출력)
- 종료 조건
  - `statusOf` 실패(미등록 프로젝트 등) → 예외, `DELETE` 시도하지 않고 중단
  - `removeProject` 실패 → 예외, DNS 삭제 시도하지 않음
  - `removeProject` 성공 후 DNS 삭제 실패 → 예외(`deployer 등록/컨테이너는 제거되었지만 DNS 레코드(<domain>) 삭제에 실패했습니다`)
  - 정상 완료 시 완료 로그 2줄(제거 완료 + workflow 파일 수동 삭제 안내) 출력

### 9. `hoster doctor`

- 형식: `hoster doctor`
- 플래그: 없음
- 동작 요약: 상태를 변경하지 않고 (1) SSH 접속·docker 권한 사전점검(`planInit`의 `ssh-docker-precheck`), (2) `docker compose version` 확인(`compose-check`), (3) `hoster-net` 외부 통신 진단(`network-diagnostic`)만 재실행. `~/.hoster/config.json`을 읽으므로 `hoster init` 선행 필요
- 종료 조건
  - SSH 접속/docker 권한 점검 실패 → 즉시 예외(`NAS 접속/docker 권한 점검 실패: ...`)
  - `docker compose version` 확인 실패(`nas.exec` throw) → 예외
  - `hoster-net` 외부 통신 진단 실패 → 경고만 출력(`warn`), 정상 종료(exitCode 변경 없음)
  - 모든 점검 통과 시 `doctor: 점검 완료 (변경 사항 없음)` 출력

## GitHub Actions 연동 계약

### 템플릿 파일

- `templates/workflow.yml.tpl` → 레포에 `.github/workflows/hoster-deploy.yml`로 생성 (`renderTemplate`)

### 치환 토큰

| 토큰 | 치환 값 (add.ts) |
|---|---|
| `{{BRANCH}}` | `opts.branch` |
| `{{PROJECT}}` | `projectName` |
| `{{IMAGE_REPO}}` | `imageRepoOf(owner, repo)` |

- `renderTemplate`은 치환 후 남은 `{{\w+}}` 토큰이 있으면 `템플릿 토큰 미지정: <목록>` 예외 발생

### 레포 시크릿 (2종, `gh secret set`으로 등록)

| 시크릿 이름 | 값 |
|---|---|
| `HOSTER_DEPLOY_URL` | `config.deployerUrl` (`https://hoster.<baseDomain>`) |
| `HOSTER_DEPLOY_SECRET` | `config.hmacSecret` |

- workflow 내부에서는 `secrets.GITHUB_TOKEN`(GHCR 로그인)도 사용하나, 이는 Actions가 자동 제공하는 값으로 `gh secret set` 대상이 아님

### 이미지 태그 규칙

```yaml
tags: |
  {{IMAGE_REPO}}:${{ github.sha }}
  {{IMAGE_REPO}}:latest
```

- SHA 태그 + `latest` 태그 동시 push

### 서명 생성 셸 코드 (원문, `templates/workflow.yml.tpl`)

```sh
BODY=$(printf '{"project":"%s","image":"%s","sha":"%s"}' \
  "{{PROJECT}}" \
  "{{IMAGE_REPO}}:${{ github.sha }}" \
  "${{ github.sha }}")
TS=$(date +%s000)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$DEPLOY_SECRET" -hex | awk '{print $NF}')
HTTP_CODE=$(curl -s -o /tmp/resp.txt -w '%{http_code}' -X POST "$DEPLOY_URL/deploy" \
  -H "content-type: application/json" \
  -H "x-hoster-timestamp: $TS" \
  -H "x-hoster-signature: $SIG" \
  -d "$BODY" --max-time 300)
cat /tmp/resp.txt
[ "$HTTP_CODE" = "200" ] || exit 1
```

- `DEPLOY_URL`=`secrets.HOSTER_DEPLOY_URL`, `DEPLOY_SECRET`=`secrets.HOSTER_DEPLOY_SECRET` (step의 `env:`)
- 타임스탬프: `date +%s000` (초 단위 epoch에 `000` 문자열 붙여 ms 단위 근사)

### 실패 조건

| 단계 | 실패 조건 |
|---|---|
| `docker/build-push-action@v6` | 빌드/push 실패 시 해당 스텝 실패로 job 실패 |
| `Notify hoster deployer` | `curl` 응답 HTTP 코드가 `200`이 아니면 `exit 1` (`[ "$HTTP_CODE" = "200" ] || exit 1`) |
| `Notify hoster deployer` | `curl --max-time 300` 초과 시 curl 자체가 비정상 종료 |


## Cloudflare API 사용 명세

- Base URL: `https://api.cloudflare.com/client/v4` (`packages/cli/src/cloudflare.ts`)
- 인증 헤더: `Authorization: Bearer <apiToken>`

### 사용 엔드포인트

| 메서드 | 경로 | 용도 | 호출 메서드 |
|---|---|---|---|
| POST | `/accounts/{accountId}/cfd_tunnel` | 터널 생성 | `createTunnel` |
| GET | `/accounts/{accountId}/cfd_tunnel/{tunnelId}/token` | 터널 토큰 조회 | `getTunnelToken` |
| PUT | `/accounts/{accountId}/cfd_tunnel/{tunnelId}/configurations` | 터널 인그레스 규칙 설정 | `setTunnelIngress` |
| GET | `/zones/{zoneId}/dns_records?name=<name>[&type=<type>]` | DNS 레코드 조회(정확히 일치하는 이름) | `findDnsRecord` (private, `upsertDnsCname`/`deleteDnsRecord`에서 사용) |
| PUT | `/zones/{zoneId}/dns_records/{id}` | 기존 DNS 레코드 갱신 | `upsertDnsCname` (레코드 존재 시) |
| POST | `/zones/{zoneId}/dns_records` | 신규 DNS 레코드 생성 | `upsertDnsCname` (레코드 없을 시) |
| DELETE | `/zones/{zoneId}/dns_records/{id}` | DNS 레코드 삭제 | `deleteDnsRecord` |

- `findDnsRecord`는 `name` 쿼리 파라미터로 조회하며(서버 측에서 `name.exact`와 동일하게 동작), `type` 지정 시(`upsertDnsCname`/`deleteDnsRecord` 모두 `CNAME`으로 좁힘) 결과는 항상 0건 또는 1건
- 응답 포맷: `{ success: boolean, result: T, errors?: { message: string }[] }` — `success: false`이면 `Cloudflare API 실패: <errors[].message 목록>` 예외, JSON 파싱 실패 시 `Cloudflare API 응답을 파싱할 수 없습니다 (status <res.status>)` 예외

### 토큰 권한 요구 (README.md)

- `Zone.DNS Edit`
- `Account.Cloudflare Tunnel Edit`

## NAS SSH 인터페이스

### 접속 파라미터

| 파라미터 | 환경변수 | 미지정 시 기본값 (`defaultNas()`, `config.ts`) |
|---|---|---|
| host | `HOSTER_NAS_HOST` | `192.168.1.100` |
| port | `HOSTER_NAS_PORT` | `22` |
| user | `HOSTER_NAS_USER` | `admin` |

- 실제 접속 명령: `ssh -p <port> <user>@<host> <remoteCmd>` (`Nas.exec`, `packages/cli/src/nas.ts`)
- 실패 시(`code !== 0`): `ssh 실패 (<code>): <stderr 또는 stdout>` 예외

### sudo docker 절대경로 규칙

- 모든 NAS 측 docker 호출은 절대경로 고정: `sudo -n /usr/local/bin/docker <args>` (`Nas.docker`, `HOSTER_NET_CREATE_CMD`, `composeUpCmd` 등)
- `-n`: 비대화식(NOPASSWD sudoers 설정 필요, `sudo -n /usr/local/bin/docker` NOPASSWD 권한 — README.md)
- 예: `sudo -n /usr/local/bin/docker network create hoster-net`, `sudo -n /usr/local/bin/docker compose --env-file .env up -d`

### tar over ssh 전송 (`Nas.transferDir`)

1. 로컬: `tar -cf - -C <parent> <name>` 실행, stdout을 **Buffer**로 직접 수신(문자열 왕복 시 0x80 이상 바이트 손상 방지)
2. 원격: `tar -C <remoteParent> -xf -` 실행, 위 tar Buffer를 stdin으로 전달(`Nas.exec(cmd, stdin)`)
3. `hoster init`에서는 `STATE_DIR_CMD`(`mkdir -p /volume1/docker/hoster/state/env`) 실행 후 `stack/` → `/volume1/docker/hoster-tmp`로 전송, 이어서 `cp -a` + `rm -rf`로 최종 위치(`/volume1/docker/hoster`)에 반영

### shQuote 인용 규칙 (`packages/cli/src/shell.ts`)

```ts
export function shQuote(value: string): string {
  return `'${value.replace(/'/g, "'\\''")}'`;
}
```

- POSIX 표준 기법: 값을 작은따옴표로 감싸고, 값 내부의 작은따옴표는 `'\''`(닫는 따옴표 + 이스케이프된 리터럴 따옴표 + 여는 따옴표)로 치환
- 적용 원칙(`commands/init.ts` 주석): NAS/로컬 셸 명령에 보간되는 모든 값(NAS host/user/port 포함)은 예외 없이 `shQuote`를 거침
- `substitutePlaceholders(template, values)`: `${KEY}` 형태 플레이스홀더를 `shQuote(value)`로 치환. `String.replaceAll` 대신 `split/join` 사용(교체 문자열의 `$&`/`$$` 특수 패턴 해석 방지)
